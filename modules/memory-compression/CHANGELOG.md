# memory-compression changelog

What changed in each version, newest first, in plain words. The numbers are explained in [tools/versions/README.md](../../tools/versions/README.md): the API number goes up only when someone using an older copy could be affected.

## 2.0.1 · API 2 · 2026-10-18
Opening a file in fast mode is faster in Firefox 158, WebKitGTK 2.52.6 and GNOME Web 46.5 when files of other modes are also opened on the same page. Number columns open 34% to 40% faster in Firefox (counters 0.80 to 0.48 ms), user records open 21% faster in Firefox, 25% in WebKitGTK and 24% in GNOME Web, and the seven number columns of the test set open 64% faster in WebKitGTK and 65% faster in GNOME Web (16.7 to 6.0 ms and 16.6 to 5.9 ms). Chromium 155 is unchanged within noise. Packed files are identical, byte for byte, and the file grows by 846 B (276,468 to 277,314 B). What changed: three copy loops now have one copy per kind of typed array, so each loop sees one array type (Firefox slowed down when one loop saw several).

Tested in: ungoogled-chromium 155.0.8059.39-1, Firefox 158.0, WebKitGTK 2.52.6, GNOME Web 46.5

## 2.0.0 · API 2 · 2026-10-17
Two modules become one file. memory-compression (bytes and typed arrays, last 1.1.0) and memory-compression-jso (plain JavaScript objects, last 1.4.1) are now the single file memory-compression.js, and the separate memory-compression-jso module is retired. A page that loaded both now ships about 270 KB (83 KB gzipped) instead of about 360 KB (115 KB gzipped): 25% smaller and 27% smaller (smaller is better). New: one pack(), unpack() and view() that choose the layer by themselves, from the kind of thing you pass: typed arrays and bytes go to the packing core, lists of records, text and other objects go to the object layer, and a number typed array goes to the number picker with mode balanced (or all three ways compared, smallest kept, with mode small). opts.layer = 'core' or 'objects' forces a layer. Not done yet, and said plainly: the module does not look inside a typed array to guess whether the picker would win, and does not pick fast, balanced or small by size or time budget. The global MemoryCompressionJSO stays as an alias for the object layer, so code written for memory-compression-jso keeps working; files packed by 1.1.0 and 1.4.1 open unchanged (checked in Node with the old files, byte for byte). The packing code itself did not change: the same bytes come out. API 2 because the module was renamed and merged and small mode on a typed array can now answer with a smaller picker container. Tests: 24 checks for the core, 38 for the object layer and 13 for the new entry point.

Tested in: ungoogled Chromium 155.0.8059.39-1, Firefox 158.0, WebKitGTK 2.52.6 and GNOME Web 46.5, one at a time (2026-10-18): the object layer's 38 checks and the new entry point's 13 checks inside each browser page, 51 of 51 passed in all four, WebAssembly on (3.2 to 3.4 s per browser for the checks). Node 22: packing core 24 checks, object layer 38, entry point 13, with and without WebAssembly. Not run: the demo pages, the benchmark pages, a phone

## History before the merge

Until 2.0.0 this module was two: **memory-compression** (bytes and typed arrays, versions 1.0.0 to 1.1.0) and **memory-compression-jso** (plain JavaScript objects, 1.0.0 to 1.4.1, with the packing core inside). Their entries are kept here as they were written.

### memory-compression 1.x (bytes and typed arrays)

#### 1.1.0 · API 1 · 2026-10-17
Small mode now packs floats and records faster and a little smaller. A 120 MB scene packs in about 2.2 s instead of 3.6 s (1.6 times faster) and ends at 41.2% instead of 41.3%; on 16 MB test sets of floats, records and text together it runs at 84 MB/s instead of 49 MB/s (1.7 times faster) and ends at 54.8% instead of 55.4%, with grid coordinates 2.8 times faster and 3 points smaller (48.1% to 45.2%). How: on a column of bytes that varies little, short repeats are not worth taking (a repeat costs about 20 bits, a plain byte there costs a few), so it now skips them and searches far less; text is not affected. Two cases got a little worse: random-walk floats are 0.5 to 0.9 points bigger and about 15% slower to pack. Restoring and fast mode are unchanged. The JavaScript path and the WebAssembly path now cut their compressed blocks at the same place, so they give identical bytes in the rare cases where they used to differ by one byte (both always restored exactly); one new check covers it (24 in all). The WebAssembly helper grows from 21.8 KB to 24.5 KB.

Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1, WebKitGTK 2.52.6 and GNOME Web (Epiphany) 46.5, one at a time (2026-10-17): the demo page (both rows restored byte for byte at 8 MB and 32 MB; small-mode pack at 32 MB took 432 ms in Firefox, 300 ms in Chromium, 338 ms in WebKitGTK and 299 ms in GNOME Web); Chromium 155 also the repo test run. Node 22.22.0: 24 checks with and without WebAssembly, the long fuzz, and the WebAssembly file rebuilt from source (byte-identical). Not run: the full benchmark page, a phone.

#### 1.0.0 · API 1 · 2026-10-17
New module. It keeps big arrays, coordinates, records and text packed in memory and brings them back exactly, bit for bit. Fast mode (a restore speed of about 0.7 to 1.1 GB/s with its WebAssembly helper, about 0.2 to 0.5 GB/s without it) makes records 39% of their size and walking floats 57%; small mode makes them 29% and 49% (fflate level 6: 46% and 74%; lz4js: 72% and 99.8%). A 120 MB scene restores in about 175 ms in fast mode (lz4js 525 ms, fflate 1.2 s, pako 1.6 s), and six such scenes took 375 MB of memory packed instead of 720 MB raw. Noisy float coordinates still only shrink 8% (fast) to 18% (small); the floats-aware pre-step is what gets small mode 8 to 25 percentage points under fflate on floats, and on text small mode is within 1 point of fflate and pako. view() restores a single 1 MiB piece of a packed array in about 1 to 2 ms, so a big array can stay packed and be read piece by piece. Measured against fflate, pako, lz4js, a WebAssembly LZ4 and a WebAssembly zstd in Node and in all three browsers: it is the smallest on floats and records (records 39% against 72% for the LZ4 packages and 49% for zstd level 3) and faster than all of them on records; the WebAssembly LZ4 restores faster on data that cannot shrink and in WebKitGTK, and zstd is smaller on text. It also reads and writes standard LZ4 blocks, deflate, zlib and gzip, readable by other tools. The WebAssembly helper is optional: where a page policy forbids it, everything still works about 1.5 to 4 times slower.

Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1 and WebKitGTK 2.52.6, one at a time: the full benchmark page (79 of 79 self-checks pass in each, every result restored byte for byte), a comparison page against fflate, pako, lz4js, lz4-wasm, zstd-wasm and CompressionStream, and the demo page; the demo page also in GNOME Web (Epiphany) 46.5 (both rows restored byte for byte at 8 MB and 32 MB); Node 22.22.0: 23 checks, with and without WebAssembly. Not run: the benchmark page in GNOME Web 46.5, a phone, a real Netflow Map scene.

### memory-compression-jso 1.x (plain JavaScript objects)

#### 1.4.1 · API 1 · 2026-10-17
Packing in balanced mode is faster, with the same files (bytes within 0.01%) and every value back exactly. Lower is better: on 12 test sets (7 number columns of 100,000 values and 5 object lists) the whole pack took 2,481 ms before and about 790 ms after (-68%); the five object lists in Node: 300,000 links 2,116 ms to 606 ms, 100,000 graph nodes 568 to 257, 200,000 log events 589 to 183, 50,000 user records 372 to 127, 20,000 map features 361 to 123. Number columns of 100,000 values, balanced pack in Chromium 155: timestamps 88.4 ms to 21.4, 2-decimal prices 87.8 to 21.5, decimals with float noise 175.2 to 52.5; in Firefox 158: 60.0 to 17.8, 58.3 to 15.8, 115.7 to 36.6; in WebKitGTK 2.52.6: 52.0 to 17.0, 59.0 to 17.0, 106.7 to 33.0; in GNOME Web 46.5: 48.3 to 14.6, 61.0 to 17.0, 108.3 to 40.0. So balanced now packs 2 to 7 times slower than fast, not 7 to 24 times.
How: nested coding goes 2 levels deep instead of 3 (gave 0.04% on the test sets and cost 1.7 times the time); the plain-doubles way is only built when nothing else is smaller; the byte-plane variant is picked on a quarter of the block; the entropy coder is skipped when its estimate cannot beat the best size so far; the table of values uses a lookup table instead of a Map for narrow ranges; after the first two blocks of a column, three blocks in four try only the ways that won before (every fourth block tries everything); the entropy coder divides by multiplying with the reciprocal.
Also faster: reading a balanced file of 300,000 links 162 ms to 134 ms (byte planes are put back through a 32-bit view). One column of 1-decimal temperatures came out 1.9% smaller (54,325 to 53,295 bytes). The file grew 7,759 bytes (264,415 to 272,174). small mode is faster again: it used to try a second pass (no entropy coding, then deflate) on every long column, and that pass almost never wins; it is now tried only when the first 8,192 numbers show it coming within 2% of the first pass (and skipped when it would write the very same bytes). Five lists (300,000 links, 100,000 nodes, 200,000 events, 50,000 users, 20,000 features) in Node, warm, best of 3: 2,343 ms to 1,440 ms (-39%, lower is better), 300,000 links 1,316 to 620 ms; files 0.003% bigger in all (11,407,586 to 11,407,889 bytes). Real-valued columns (decimals with many digits, such as map coordinates) also pack faster: four columns of 200,000 doubles took 336 ms in 1.4.0 and about 105 ms now (-69%, lower is better) with byte-for-byte the same files (4,006,009 bytes in all); a smooth-drift column of 100,000 doubles 39.0 ms to about 16 ms, same 559,650 bytes. How: one pass counts each byte plane and the counts are reused, the plain-doubles way is tried last and only when nothing else is under 6 bytes per value, and the dictionary way is skipped when a sample shows many distinct values. New: keeper.each(name, fn) hands a packed array of objects out 2,048 rows at a time without ever making the whole list (300,000 links: 17 MB of extra live memory in Node against 66 to 68 MB for get() or restore(), lower is better; longest page freeze 17 to 27 ms in the four browsers, 48 to 170 ms in all), and view.slice(from, to) makes just those rows. Fixed: a Node program that used restore() did not exit afterwards (it now yields with setImmediate in Node). small mode now also chooses on a sample, as balanced does: five 100,000-row lists pack in 1,323 ms instead of 1,751 (-24%, lower is better) and come out 0.09% bigger (6,463,327 to 6,469,065 bytes); the decimal way gives up as soon as half the values in a block are not decimals. Not changed: fast mode, the format (still 5), the other keeper calls.

Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1, WebKitGTK 2.52.6, GNOME Web 46.5 (the module's own 38 checks inside each browser page, one browser at a time, 38 of 38 passed in all four, 3.6 to 4.6 s of checks each and 10 to 23 s with browser start-up, run again on the JS-modules main tree 2026-10-18; number-column and restore timings one browser at a time, from the research runs; tests in Node: normal, no-wasm, no-eval, full fuzz)

#### 1.4.0 · API 1 · 2026-10-17
One file now covers everything: the number chooser, the keeper and the profile hooks are inside memory-compression-jso.js (264,415 bytes, was 215,502 bytes in 1.3.0: 48,913 bytes larger, 23% (smaller is better); the plain-JavaScript fallback gives the same bytes when a page blocks WebAssembly).
New: mode 'balanced' (and 'small', or picker: true in fast mode). Each block of 8,192 numbers is tried several ways on a sample and the smallest is written: constant, offset and width, differences, runs, a table of values, a few big exceptions, a shared divisor, entropy coding, decimals stored as whole numbers (float-noise values kept as a tiny distance from the decimal), raw, and byte planes. Smaller is better: 100,000 ids 1,635 to 121 bytes (-92.6%), rising timestamps 71,052 to 20,548 (-71.1%), 2-decimal prices -26.4%, 5-decimal coordinates -30.3%, 1-decimal temperatures -44.0%, decimals with float noise -61.0%, random doubles 0.0% (kept as is). Whole lists of objects in Node: 300,000 links -16.4%, 100,000 graph nodes -15.5%, 200,000 log events -27.9%, 50,000 user records -17.7%, 20,000 map features -22.6%. The cost, lower is better: packing takes 7 to 24 times longer (300,000 links 87 ms to 2,116 ms), reading 1.0 to 3.6 times longer (68 ms to 248 ms), the same in all four browsers within noise. Default mode 'fast' is unchanged: same bytes as 1.3.0 on all 5 data sets, pack time within 5% (noise).
New: text columns with few distinct values (dictionaries) send their numeric codes through the same chooser when balanced or small is on. Files that use the chooser say format 5; 1.3.x refuses them with 'made by a newer version', fast-mode files keep their old format numbers.
New: keeper({ budget, onPressure, ... }) holds named values packed. hold, get, view, column, restore, pin, unpin, calibrate, memory, trim, release, drop, level, bytes, adopt, names, has, touch, heap. restore(name) gives the value back in slices of about 8 ms so the page stays free: for 300,000 links the longest freeze is 21 to 31 ms in the four browsers (get() freezes it for 53 to 76 ms). pin(name) keeps an item from being trimmed while it is drawn. calibrate(factor) scales the live-size guess (a browser page can cost 2.5 times a plain heap count). memory() lists packed size, restored size and restore time (guessed before the first restore, measured after). Reading single links from a packed list: the first read opens the columns (36 to 115 ms), each read after that takes 0.2 to 0.7 microseconds (the first study measured 220 microseconds each). A worker was tried for restoring and dropped: it froze the page 187 to 299 ms and took 5 to 10 times longer.
New: profile(value, options, repeats) returns pack and unpack milliseconds, the format and where the time and bytes go by column; estimateBytes(value) guesses live size; heap() reports what the browser offers (Chromium only; Firefox and Safari report nothing, so the keeper counts for itself). The global MemoryCompression is also set (the core alone) when the page has none.
Removed: the optional extra-coder add-on file and its option; the chooser does not depend on it. A file made in 1.2.0 or 1.3.0 with the add-on is refused with a plain message (read it with 1.3.0).

Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1, WebKitGTK 2.52.6, GNOME Web 46.5 (the module's own 36 checks inside each browser page, one browser at a time, 36 of 36 passed in all four, 5 to 8 s each; number columns, restore and single reads measured in each earlier; tests in Node: normal, no-wasm, no-eval, long fuzz)

#### 1.3.0 · API 1 · 2026-10-17
Sorted text columns (file paths, word lists) are stored as the part shared with the row above plus the new end: about 41% smaller on 40,000 file paths and 31% on 30,695 words (smaller is better), kept only when a column gains 15% or more, off with front: false; those columns take about 1.3 to 1.8 times as long to pack and read. ISO date text now unpacks about 1.9 times faster in WebKitGTK and GNOME Web with millisecond stamps (4.6 to 2.5 ms and 5.8 to 2.8 ms per 20,000 rows). Files that use the new way say format 4 and older copies refuse them.

Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1, WebKitGTK 2.52.6, GNOME Web 46.5 (the speed table below; tests in Node, normal, no-wasm, no-eval and full fuzz)

#### 1.2.0 · API 1 · 2026-10-17
New: dates and times as text become one number. A column of ISO dates (2025-03-05T04:15:00Z, with milliseconds, date only, or with a space) is stored as one number per row instead of six and comes back as the same text; a row that is not a real date keeps the old way. Files are smaller (smaller is better): 20,000 sorted log timestamps 20.4 KB to 15.9 KB (22% smaller), 20,000 random dates 51.9 KB to 35.8 KB (31% smaller), 50,000 random dates and times 241.5 KB to 181.2 KB (25% smaller). A steady one-per-hour column stays at about 87 KB (0% change). Unpacking 20,000 sorted timestamps is faster in Firefox 158.0 (2.7 ms to 1.4 ms) and ungoogled Chromium 155 (1.6 ms to 1.3 ms) but slower in WebKitGTK 2.52.6 (2.3 ms to 3.6 ms) and GNOME Web 46.5 (2.5 ms to 3.3 ms); packing in WebKitGTK is 1.15 to 1.5 times faster (6.9 ms to 6.0 ms). A date column is used only when one number is expected to cost no more than the separate ones.
New: number-column arrays are reused between packs (at most 48 MB kept; pack(x, {pool: false}) turns it off, freeBuffers() empties it). Measured: 300,000 links pack about 1 to 6% faster in Node (85.0 ms to 79.6 ms, median of 41 alternating runs); no other set moved by more than the noise of about 5%.
New: fsst: true (off by default). A text column of short, varied strings (names, paths, log lines) is stored as FSST codes: a table of up to 255 learned text pieces plus a few bytes per string, instead of the joined text. Files are smaller (smaller is better): 20,000 names and cities 180.5 KB to 89.3 KB (51% smaller), invented words 119.4 KB to 56.8 KB (52%), file paths 247.1 KB to 110.3 KB (55%), log messages 234.5 KB to 153.9 KB (34%), 100,000 names and cities 902.0 KB to 423.8 KB (53%). Any one string can be read alone: view() keeps such a column at about a third of its restored size (555 KB to 166 KB for 20,000 names, 2,777 KB to 810 KB for 100,000, 3.3 to 3.4 times less) and opening a view plus reading the first field takes 0.53 ms instead of 4.75 ms in Firefox (9 times faster; 1.5 to 2.7 times faster in the other three browsers and Node); one string read takes 0.15 to 0.55 microseconds. Cost: packing is 1.9 to 6.4 times slower (about 14 to 24 ms against 2 to 8 ms for 20,000 rows) and unpacking the whole column is 1.0 to 1.6 times slower. Each text column is tried both ways and the smaller is kept, so patterns, small dictionaries and repeating whole values keep their own way. A 3 KB WebAssembly helper does the text-to-codes work from 4,096 rows: packing 1.2 to 1.8 times faster (18.3 ms against 28.7 ms in Firefox), unpacking 1.2 to 3.2 times faster (8.4 ms against 26.5 ms for 100,000 names in Chromium); plain JavaScript writes the same bytes.
New, withdrawn again in 1.4.0: an extra number coder through a separate optional add-on file (441 KB). Each number column of 4,096 values or more was also tried with it and the smaller kept. Files were smaller (smaller is better): 100,000 sensor-style rows 1,537.3 KB to 508.5 KB (67% smaller), price ticks 289.1 KB to 154.2 KB (47%), random coordinates 1,677.6 KB to 1,200.2 KB (28%), 100,000 links 2,640.2 KB to 2,207.6 KB (16%); packing was 1.2 to 3.5 times slower (lower is better). It was off unless asked for and is gone; the built-in chooser now covers number columns.
Files with a date, FSST or add-on column are format 3: 1.1.x refuses them with a clear message; files without one are unchanged (format 2). Format 3 files are read by this version, which also reads formats 1 and 2.
Not built, with the number: folding the repeated-text lookup into the splitting pass saves about 2 ms of an 85 ms pack in isolation (2%), below the noise. Not changed: sizes of number-only sets without the add-on, the plain way of packing text.
Built for a later per-column picker: every column already says which method stored it (plain, date, FSST, add-on) and the writer keeps the smallest, so another method can be added as one more column type.

Tested in: Node 22.22.0 (31 checks with and without WebAssembly, and the long random test); Firefox 158.0 (reports 158.0b5), ungoogled-chromium 155.0.8059.39-1, WebKitGTK 2.52.6, GNOME Web 46.5, one at a time, a fresh page for each data set; not run: a phone, a real Netflow Map scene

#### 1.1.0 · API 1 · 2026-10-17
New: text patterns. Strings that follow a pattern ('user7@example.org', '2025-03-05T04:15:00Z', 'Item 12 flow') are stored as the pattern once plus a column of numbers. Files are smaller: 50,000 user records 1.080 MB to 0.764 MB (29% smaller), 200,000 log events 2.481 MB to 1.670 MB (33% smaller), 100,000 scene items 2.652 MB to 2.099 MB (21% smaller); number-only sets such as the 300,000 links stay at 7.854 MB. Small mode packs the events 1.5 times faster (174 ms to 117 ms, Node). In a browser the extra step makes text-heavy packing about 1 to 4 ms slower at 10,000 to 40,000 rows (for example 6.3 ms to 7.7 ms in Firefox 158.0); pack(x, {patterns: false}) skips it and gives the old speed back.
New: shared objects stored by column. With refs: true, 100,000 items and 300,000 links that point at the item objects come out at 2.49 MB instead of 5.78 MB (2.3 times smaller) and pack in 228 ms instead of 484 ms (2.1 times faster); unpack 122 ms instead of 166 ms. msgpackr with its structure-clone option needs 11.49 MB for the same graph.
New: view() opens without restoring anything. Opening a view of 300,000 links takes about 0.06 ms instead of about 29 ms; a column is restored the first time it is read (one column of the links, about 1.4 ms), and the new loaded(), memory() and release() calls show and free the restored columns. An open view holds the packed 7.5 MB until a column is read (the live objects take 116 MB). Files made by 1.0.0 still open, restored all at once as before.
New: float32: true (off by default, lossy). Columns of fractions are kept in 4 bytes per value instead of 8: the 300,000 links go from 7.85 MB to 5.57 MB (29% smaller), worst relative error 6.0e-8.
New: patterns: false option, described above.
Faster with WebAssembly: a 608-byte helper reads big text columns (4,096 rows and up); the plain-JavaScript loop gives the same bytes. Pack, fast mode, WebAssembly on against off, Node: 300,000 links 83 ms against 112 ms; small mode 227 ms against 353 ms.
File format 2: a table of column sizes lets a view find one column without reading the others. A 1.1.0 file cannot be read by 1.0.0 (older files are read by 1.1.0, checked with a stored 1.0.0 file).
Not changed: the exact-restore rule, the sizes of number-only sets, irregular data (still 37% of the JSON text). Browsers: WebKit (WebKitGTK 2.52.6, GNOME Web 46.5) still packs text-heavy sets 1.7 to 2.3 times slower than msgpackr with records; not fixed.

Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1, WebKitGTK 2.52.6 and GNOME Web (Epiphany) 46.5, one at a time: the comparison page and the demo page; Node 22.22.0: 26 checks with and without WebAssembly plus the long random test. Not run: a phone

#### 1.0.0 · API 1 · 2026-10-17
New module. It keeps a big list of plain JavaScript objects packed in memory and brings every value back exactly (numbers including NaN and -0, text, booleans, null, undefined, BigInt, Date, Map, Set, RegExp, typed arrays and nested objects; shared objects and cycles with refs: true). Arrays of 16 or more objects are stored by column, so key names are written once and the numbers go through memory-compression's float-aware packing. In Node 22.22.0, 300,000 link objects (57.3 MB of JSON text) become 7.9 MB (13.7%) in about 126 ms and unpack in about 84 ms; msgpackr with records makes 20.0 MB (34.9%) in 130 ms and unpacks in 139 ms. Over 7 data sets, fast mode is 1.5 to 5.3 times smaller than msgpackr with records and packs and unpacks within 10% of it or faster on 6 of 7 (50,000 user records are the exception: 1.7 and 1.4 times slower); small mode is another 15 to 36% smaller. Kept packed, 100,000 scene items take 2.5 MB instead of 55.8 MB of live objects (22 times less), and view() reads single items (about 0.5 microseconds each) or whole columns without making the other objects. Weak spots: data where every item is different (37% of the JSON text, speed about even with msgpackr) and WebKitGTK, where packing was 1.1 to 2.3 times slower than msgpackr with records on 6 of 7 sets.

Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1 and WebKitGTK 2.52.6, one at a time (2026-10-17): the comparison page against the other libraries (7 data sets, every result restored and compared value for value) and the demo page; GNOME Web (Epiphany) 46.5: the demo page. Node 22.22.0: 20 checks with and without WebAssembly and the long random test (4,000 cases). Not run: the comparison page in GNOME Web, a phone, a real Netflow Map scene.
