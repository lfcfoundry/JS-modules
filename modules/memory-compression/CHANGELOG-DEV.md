What changed in each version, newest first, for developers, in three depths: Quick (what changed and whether old code breaks), Details (API, numbers with the browser named, how to upgrade) and Deep (design reasons, tests, what was tried). Users read CHANGELOG.md. The API number goes up only when someone using an older copy could be affected.

## 2.8.0 · API 2 · 2026-10-31

### Quick
New default autoTries: whole-number columns of up to 100,000 values try every number coding on their first block only. Pack 1.02 to 1.24x faster, files 0 to 1.3% bigger on such lists; `autoTries: false` gives the 2.7.0 bytes. Old files open the same.

### Details
The owner picked "Yes, automatic" on the card (2026-10-31). The number picker (packRun) gets `auto` from the object layer: when the first block of a column comes out as whole numbers, the column counts as stable and later blocks skip the full tries as quickTries does, but only while the column has at most 100,000 values; a stable column re-checks every way every 32nd block (was every 8th). A block far worse than the one before (99x the bytes per value) would turn the full tries back on. packAsync workers get autoTries too. Byte-identical to the research build (memory-compression-auto4) on 30 list/option pairs in Node. tests/memory-compression-auto-browser.js: 2.8.0 against autoTries: false, mode 'balanced', 9 rounds, then 21 rounds for the cells that looked slower.

### Deep
Pack ms, autoTries vs false (x faster), bytes: links 60k Chromium 1.12x, Firefox 1.16x, WebKitGTK 1.05x, +0.30%; events 40k 1.24/1.13/1.09x, +1.13%; users 20k 1.02/1.11/1.15x, +0.27%; events 100k 1.19/1.12/1.12x, +1.30%; links 150k 1.12/0.99/1.05x, +0.13%; events 300k 1.07/1.02/1.03x, 0.00%; users 150k 1.10/1.23/1.06x, -0.03%. The first 9-round run showed Chromium events 100k at 0.91x and 300k at 0.94x and Firefox events 40k at 0.91x; at 21 rounds they were 1.19x, 1.07x and 1.13x (noise). Research history: an 8% worse-block guard, a margin gate and a runner-up hedge were tried and dropped (each spent the time back); the range cap kept the gain where it is.

## 2.5.0 · API 2 · 2026-10-23

### Quick
Column pages hold text lazily: page open up to 45% faster, held text columns 62 to 89% smaller; a column read row by row is made in one pass, so reading rows costs about what it did in 2.4.9; memory report counts text and nested data.

### Deep
memory-compression 2.5.0 makes column pages hold text lazily, keeps reading rows as cheap as before by turning a column that is read row after row into its strings in one pass, and makes the memory report honest. It is the work briefed as 2.4.4 (lazy text columns); 2.4.4 is a reserved number and 2.4.9 already exists on this branch, so it ships as the next feature release, 2.5.0. No format change: old files open, new files are the same bytes. Built file 373,998 to 379,361 B (+5,363 B, +1.4%). This entry replaces the first 2.5.0 entry of the same unmerged pull request (one release, not two).

1. Lazy text in column pages. view() (and so the pager's pageView pages) keeps top-level text columns whole until a row is read: plain text stays one decoded string plus a 4-byte row end per row (a string is cut out when a row asks for it), pattern text such as "Item 12 flow" stays the pattern, its numbers and small lookup tables and is put together per row. Pattern text needs generated code; on a page that forbids it (or with MEMORY_COMPRESSION_NO_EVAL) it is built at open as before, so no new policy need. Nested text, dictionary text, dates and number columns are untouched; unpack() is unchanged.

2. Row cache (the mitigation). Cutting one string per get(i) cost 37 to 129 ns a row more than 2.4.9 (first 2.5.0 build; one build per page: reads +23 to +135% in Chromium and Firefox, +117 to +200% in WebKit browsers). A text column that has been read n/32 times (at least 32; lists up to 16,384 rows) is now turned into its strings in one tight pass, becomes a plain column and later reads cost what any column costs. A page opened and read for a row or two stays whole, so the page-open and memory gains stay. Col.get is back to a small body (modes 0 to 3, one fall-through), one Col class, so no polymorphic call sites. Given up: a page whose text columns are read right through holds its strings again (memory back to the 2.4.9 level: Scene items 306 vs 306 KB Chromium heap, 453 vs 453 KB Firefox; User records 377 vs 378 / 578 vs 576) and the work of making them moves from open to the first scan (open plus reading every row is within the 2.4.9 cost or better in all four browsers, see below). Columns above 16,384 rows are not made in one pass (a read must not wait for it), so a long list read row by row keeps the lazy per-row cost; the slices of unpackAsync stay short.

3. Page open and memory gains kept (one build per page, 3 fresh passes of 40 rounds, medians, lower is better): page open Scene items 0.39 to 0.30 ms Chromium (-24%), 0.44 to 0.37 Firefox (-17%), 0.64 to 0.50 WebKitGTK (-22%), 0.64 to 0.50 GNOME Web; Log events -26%, -45%, -14%, -14%; User records -14%, -8%, -12%, -15%. Held page memory (all columns restored, one row read; Chromium heap / Firefox page zone, KB per page, 2.4.9 to now): Scene items 304 to 207 (-32%) / 453 to 395 (-13%); User records 376 to 305 / 575 to 545; Log events 105 to 12 (-89%) / 120 to 46 (-62%).

4. Chromium Map features page open +61% and pager +143% (first 2.5.0 report): found to come from the test harness, not the module. Two builds in one page share V8's compiled copy of every generated function whose source text is the same, and so its type feedback; giving each build's generated code a distinct comment removed the gap (+39 to +52% became 0 to +8%), and a build alone in a page shows 2.12 / 2.09 / 2.07 ms for 2.4.9 / 2.5.0 first build / this one. Nothing to fix in the module. (A same-page A/B also hides the read cost above, because the loop's get() call site sees three builds; the tables here use one build per page, taking turns across fresh browsers.)

5. Memory report. view().memory().restored counts what the open columns take: 32 bytes for a long string cut from a bigger text, shared text once, dictionary tables, nested arrays and objects, the lazy columns, the strings of a column that has been made, and 8 KB for the open view. Against real memory the estimate still goes the two ways of the two engines: Firefox real vs report (KB per page, held / read right through): Scene items 395 vs 324 / 453 vs 395, User records 545 vs 450 / 576 vs 495, Log events 46 vs 47 / 132 vs 138 (80 to 87% on pages with small nested arrays, whose objects Firefox makes about twice as large as the estimate); Chromium counts about 6 to 19% above its JS heap on the same pages (number columns are outside its heap). Not changed: one constant cannot fit both engines.

6. Checks. 73 checks pass (72 before: new "a text column read row after row is turned into its strings", the FSST check asks for the memory number before the whole page is read) in quick, FULL=1, --js-only and under --disallow-code-generation-from-strings; node tests/kits.js --quick --only memory passes. Packed bytes identical to 2.4.9 in 126 of 126 cells (and packAsync), with generated code allowed and refused; view get/field/column/slice/toArray, read every row in turn, equal unpack().

### Deep
Two modules become one file. memory-compression (bytes and typed arrays, last 1.1.0) and memory-compression-jso (plain JavaScript objects, last 1.4.1) are now the single file memory-compression.js, and the separate memory-compression-jso module is retired. The packing code itself did not change: the same bytes come out. API 2 because the module was renamed and merged and small mode on a typed array can now answer with a smaller picker container.
