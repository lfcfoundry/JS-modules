netflow-engine

The engine of Netflow Map as a module you can copy and adapt: nine views of a map and eleven network layouts, no two items on top of each other, WebAssembly twins for Force and Distances, and a use() hand-over for the layers and Sankey add-ons; a 30,000-item network lays out in about 0.8 s in the Netflow Map app (Firefox).

What it is and how it works

The engine of Netflow Map as a module you can copy and adapt. You give it items and links; it works out where everything goes and hands back plain numbers ready to draw.

  • Data is prepared into flat typed arrays, with choke points and traffic found first.
  • Items are placed with a layered, force or distance-based method, or as a story in rows, arcs, a matrix or a shape.
  • Heavy steps run in WebAssembly when allowed, with identical results in JavaScript. It needs no page, so it runs in a worker or Node.

Why it exists

Netflow Map's gains live in its engine: a 30,000-item network went from 42 seconds to under a second in one week. Every significant engine update is published here so others can adapt it for their own cases.

Where it helps

  • Network and flow maps in your own app.
  • Laying out large graphs off the main thread.
  • A starting point for custom layouts with add-ons.

Not for: drawing; it returns positions, not pictures.

How it compares

Run on 2026-10-18 against d3-force 7.9.0, Cytoscape cose 3.34.4, dagre 0.8.5 and ELK (elkjs) 0.12.0, each with its default options, in ungoogled-chromium 155.0.8059.39-1, Firefox 158.0, WebKitGTK 2.52.6, one browser at a time. Every case is a fresh page under script-src 'self' 'wasm-unsafe-eval'; 3 runs per case (a case over 20 s ran once); 60 s limit per case. The networks are generated from a fixed seed. Speeds are from the browsers only.

In short: the engine was faster in every case that finished, in all three browsers (higher is better for the engine): 3.2x to 4.8x faster than d3-force, 20.8x to 93.6x than Cytoscape, 304x to 614x than ELK's stress layout (300 items; nothing larger finished), 9.8x to 243x than dagre and 17.9x to 138.7x than ELK's layered layout. Where it gives something up:

  • Cytoscape's force layout has slightly lower stress at 300 and 1,000 items (by 0.001 to 0.011, lower is better), and takes 21x to 94x longer; at 3,000 items it went over 60 s in all three browsers.
  • ELK's layered layout has fewer crossings at 1,000 items (6,471 against 6,499, about 0.4% fewer) and at 3,000 items (35,909 against 37,247, about 3.6% fewer). At 300 items the engine has the fewest (559 against ELK 632 and dagre 784).
  • ELK's stress layout needed 15.9 s to 26.4 s for 300 items (one run each) and went over 60 s at 1,000 and 3,000; its stress at 300 was 0.170 against the engine's 0.161.

How to use it

<script src="netflow-layers.js"></script>   <!-- only for the story views (Flow, Top-down, Spine, Lanes, Sankey, Arc, Matrix); the Network view does not need it -->
<script src="netflow-engine.js"></script>
var graph = { start: 'a', nodes: [{ id: 'a', label: 'Start', group: '', valence: '', ghost: false, attrs: {} },
                                   { id: 'b', label: 'Next',  group: '', valence: '', ghost: false, attrs: {} }],
              edges: [{ from: 'a', to: 'b', label: '', kind: '', attrs: {} }] };
var L = NetflowEngine.build(graph, { view: 'network', arrange: 'stress', colorBy: 'group' });
// L.nodes: one record per item with its place (cx, cy for the Network view; x, y for rows), size and color value
// L.edges: one record per link; L.groups: the groups; L.ms: how long the build took

Putting a big layout back (saved layouts)

A Network layout of a big map is slow to compute and quick to put back. NetflowEngine.layoutKey(graph, options) returns a short fingerprint string of everything that decides the picture (the data, the options, the tuning and the layout code itself; null for views and options where saving makes no sense, such as previews). Keep the finished positions anywhere you like, for example in IndexedDB, under that key:

var key = NetflowEngine.layoutKey(graph, opts);
var L = NetflowEngine.build(graph, Object.assign({}, opts, { saveKey: key, wantSave: true }));
if (L.saveLayout) store(L.saveLayout);              // { key, xy: Float64Array of x,y per item, width, height, rough }
// later, for the same map:
var L2 = NetflowEngine.build(graph, Object.assign({}, opts, { saveKey: key, saved: fetched }));
// L2.fromSaved === true when the record matched; the picture is the same positions as a new layout. A wrong or damaged record is ignored and the layout runs as usual.

Netflow Map does this for maps of 1,500 items or more, reopening them 2.4 to 14.9 times faster (higher is better) with the same picture.

In Node: const E = require('./netflow-engine.js'); E.use('layers', require('../netflow-layers/netflow-layers.js')); (the layers module is also found on its own when it sits next to this folder).

Good to know

Limits

  • Story views need netflow-layers. The Sankey look needs an add-on with options, layout and apply (see above; netflow-sankey 2.1.0 or newer has all three).
  • It does not draw anything. Drawing (WebGL 2, plain canvas) lives in Netflow Map itself and is not part of this module.
  • Item and link records follow Netflow Map's data shape (nodes with id, label, group, valence, ghost, attrs; edges with from, to, label, kind, attrs, optional weight). Importers for CSV, JSON and other formats are in Netflow Map, not here.
  • The first layout in a fresh worker is slower than later ones (WebAssembly warm-up). Netflow Map warms its worker when idle; a page using this module can do the same by building a small map once.

More

Views and arrangements

NetflowEngine.VIEWS lists the nine view ids in this order: flow, down, spine, lanes, shape, sankey, arc, matrix, network. In 1.0.0 the sixth id had another name; 2.0.0 knows only sankey (an old id draws the Flow picture, like any unknown id). The Shape view returns segs and spine (stretches between choke points) and no nodes. For network, arrange picks the method: stress (Distances, the default for big maps), closeness, force, radial, circle, rings, groups, grid, stress3d (Distances 3D), force3d, sphere, stack (NetflowEngine.ARRANGE_NAMES has the names; arrangeAdvice() says which fits a given map). Other options: colorBy, sizeBy, widthBy, edgeColorBy, laneBy, agg, mode, amounts (see the comment above build in the file).

spread: "wide" (Flow, Top-down, Spine and Lanes only; needs netflow-layers 1.3.0 or newer, an older copy ignores it) draws the story views looser and more like a tree for wide screens: more room beside each box, and a box over the middle of the boxes it leads to. "tight", or leaving it out, is the compact picture as before. Handy as a switch next to the view list.

Add-ons

  • Layered drawing (netflow-layers 1.2.0 or newer; 1.3.0 for spread: "wide"): required for every story view. Found as a global NetflowLayers, or as ../netflow-layers/netflow-layers.js in Node, or handed over with NetflowEngine.use('layers', impl). If it is missing, the view that needs it throws a message that says so; the Network view still works.
  • Sankey add-on: optional (netflow-sankey 2.1.0 or newer). NetflowEngine.use('sankey', impl) and pass sk options to the Sankey view; without it the Sankey view keeps the plain layered picture. The Sankey view calls three things on the add-on: options(sk), layout(layered, options) and apply(layered, result). netflow-sankey 2.0.0 has layout but not options or apply (Netflow Map's own copy has all three), so with 2.0.0 handed over, a Sankey view that is given sk options throws "SK.options is not a function"; a Sankey view without sk options works. netflow-sankey 2.1.0 added the two calls, so use 2.1.0 or newer.
  • Your own: the engine's other parts (separate, forceSim, networkLayout, communities, metrics, taskScore) are exported so an add-on can call them. An add-on never reaches into the engine's private storage. This is the same shape the Netflow Map add-ons use.
  • NetflowEngine.columns is the column reader (numbers as people write them, dates, categories, small formulas); status() returns { placeholder: false, version, api }.

WebAssembly

The Force and Distances steps have a WebAssembly twin (forceWasm, stressWasm: each has on, minItems (150), calls, error). stressWasm also runs Distances 3D from min3d (3,000) items, the Closeness rounds from minClose (20,000) items and the hash-grid push-apart (counters calls3, closeCalls, sparseCalls); below those sizes the timings did not clearly favor WebAssembly. Flat Force starts from the Distances picture for pieces of 5,000 up to 20,000 items (force2dTuning). The flat Distances sweeps also have a two-lanes-at-a-time form (stressWasm.simd, on by default where the browser supports it; any size since 2.2.1): two neighbors in the shuffled order that share no item run side by side, so the positions are the same to the last digit; turn it off with NetflowEngine.stressWasm.simd = false. Turn one off with NetflowEngine.forceWasm.on = false; the plain-JavaScript path gives the same positions to the last digit (a check proves it). The only page-policy addition needed is 'wasm-unsafe-eval' in script-src; nothing else is loosened. Sources are in wasm/ (force.c, stress.c); sh wasm/build.sh rebuilds both (clang 18 with the wasm32 target and wasm-ld; two builds give the same bytes) and python3 wasm/embed.py puts them into netflow-engine.js.

Tests

node modules/netflow-engine/test/run.js (15 checks, about 8 seconds): every view on a 300-page story and a 1,500-item network, repeatable output, identical positions with and without WebAssembly (Force and Distances, 600 items; Distances 3D, Closeness and the hash-grid push-apart), flat Force from 5,000 items, no two items on top of each other (2,000 items, three arrangements), odd inputs (a start that does not exist, an empty map, one item), use() names, the column reader, and that the file builds no code from text. Separately, Netflow Map checks that this file gives the same layout as its own engine: 315 builds (5 maps × 9 views × 7 option sets), 0 differences.

How updates ship

  1. The Netflow Map team finishes an engine change and writes a short note (what changed, in numbers, from the three test browsers).
  2. A new version of this module is published with a plain-words changelog entry. The module's file is cut from the app's engine by tools/build-engine-module.mjs in Netflow Map, so the two cannot drift apart.
  3. Netflow Map then uses the published version. Add-ons keep their own version numbers and say which engine versions they were tested with.

Version meaning: patch for a fix, minor for something new that breaks nobody, major when someone could be caught out (the API number equals the major).

Credits

  • The engine is Netflow Map's own, by LFC Foundry. It starts from the layered, arc, matrix and shape drawings, choke points, traffic and drawing scores of the Story Editor's map (story-editor editor/maplayout.js, MIT, copied and generalized; no dependency on it).
  • Choke points use the dominator tree of Cooper, Harvey and Kennedy (2001). The Distances (stress) layout minimizes stress by stochastic gradient descent (Zheng, Pawar and Goodman, 2018) and uses far-apart pivot items for big maps. The Force arrangement uses Barnes-Hut repulsion (a quadtree in 2D, an octree in 3D). Quick groups use label propagation. The source comments name no other published method.
  • Related published pieces: netflow-layers and netflow-sankey, both cut from Netflow Map.
