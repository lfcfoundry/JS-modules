# walker-sim developer changelog

What changed in each version, newest first, for developers, in three depths: Quick (what changed and whether old code breaks), Details (API, numbers with the browser named, how to upgrade) and Deep (design reasons, tests, what was tried). Users read CHANGELOG.md. The API number goes up only when someone using an older copy could be affected.

## 2.4.0 · API 2 · 2026-10-24

### Quick
sweep and exactEndpoints now run their rounds in a second 1 KB WebAssembly program in the default file: what-if sweeps are about 40% (Chromium) and 60% (Firefox) faster, the same numbers to the last digit. New hook WalkerSim.useSweepKernel.

### Deep
Faster what-if sweeps. walker-sim-wasm.js (and the default walker-sim-with-wasm files) now carry a second WebAssembly program, built from the new wasm/sweep.c (1,047 bytes with SIMD plus a 947-byte scalar twin that is used when an engine refuses SIMD), that runs the rounds of the solver behind sweep and exactEndpoints (absorb in walker-sim.js) until the biggest change is under 1e-12 or the round limit is reached. Every number is bit for bit what the JavaScript rounds give: the ways of an item are added in the same order, the change is summed in class order, and the C is built with -ffp-contract=off. Checked on 6 random networks with loops (30 to 300 items) plus one network with long loops that needs the direct loop solver, for sweep items, sweep links, sensitivity and exactEndpoints: the WebAssembly rounds, the JavaScript rounds and a page whose code generation is refused all give the 2.3.0 numbers (pinned hashes in test/run.js), and the kernel on 200, 3,000 and 12,000 items equals a JavaScript copy of the rounds byte for byte, also after the memory had to grow. New hook WalkerSim.useSweepKernel(f) (why this is a minor step); f returns [lastChange, changeBefore, rounds] or null, and null (no WebAssembly, SIMD and scalar both refused, memory error) leaves c untouched and runs the old JavaScript rounds, which are unchanged, so the plain walker-sim.js file is not slower. The module compiles early and asynchronously like the walking loop, keeps one memory and one instance for all calls (grown only when a call needs more), and a call that finds the compile unfinished compiles on the spot. Add-on file walker-sim-wasm.js grows from 6,706 to 12,784 bytes (6.1 KB more: 3.6 KB are the two base64 programs, the rest the loader and its comments; minified 4,619 to 9,015 bytes), walker-sim.js from 61,220 to 62,427 bytes, the default file from 67,927 to 75,212 bytes. Example network (199 items, 587 links, 40 what-ifs), warm ms per call, median of 15 fresh pages, lower is better, Chromium / Firefox / WebKitGTK, 2.3.0 to 2.4.0: sweep items 16.1 / 18 / 9 to 10.1 / 7 / 8; sweep links 13.3 / 14 / 7 to 8.1 / 6 / 7; exactEndpoints 1.2 / 1.0 / 2.0 to 0.7 / 0.5 / 0.6; first call (cold) items 30.0 / 24 / 30 to 23.3 / 16 / 19. Other passes: items 15.9 / 18 / 9 to 9.1 / 7 / 8, links 12.7 / 14 / 7 to 7.7 / 6 / 6. The WebKitGTK clock steps 1 ms, so its gain is small (about 11% to 22%). run unchanged: 40 turns x 3 passes with a same-file control, 1,000,000 walkers warm 39.2 / 43 / 41 against 38.9 / 44 / 41 (control 39.1 / 43 / 42), first call 59.8 / 50 / 61 against 58.2 / 51 / 60 (control 58.3 / 53 / 61); plain walker-sim.js sweep items 16.0 / 18 / 9 against 15.5 / 18 / 9. Output of the example network identical in all three browsers (check strings 41.264980303691679 40 true for items, 40.978392633470186 40 true for links). A page without wasm-unsafe-eval: the file does nothing and sweep stays on the JavaScript rounds; the policy is unchanged.

## 2.3.0 · API 2 · 2026-10-22

### Quick
The WebAssembly loop now starts compiling in the background when the file loads; walker-sim-wasm adds wasmReady() and wasmModule().

### Deep
Compile early: walker-sim-wasm.js (and the default walker-sim-with-wasm files) start WebAssembly.compile when the file loads, and the first big run only starts the compiled module; a run asked for before the compile is done compiles on the spot as before, and with no WebAssembly nothing changes. New WalkerSim.wasmReady() (promise of true/false) and WalkerSim.wasmModule() (the compiled module or null, for a worker); WalkerSim.wasm is now a getter with the same meaning. Same counts. The program is 966 bytes, so there is little to win: load plus first use, ms, old / new, take turns, median of 9 fresh pages, right after load / 250 ms later (bigger ratio is better): Chromium 155 8.7 / 9.9 and 7.9 / 8.9 (0.88x, 0.89x), Firefox 158.0 23 / 22 and 23 / 20 (1.05x, 1.15x), WebKitGTK 2.52.6 3 / 3 and 4 / 3, GNOME Web 46.5 4 / 4 and 4 / 4. About 1 ms slower in Chromium, level or about 1 ms faster elsewhere; not measured at phone size.

## 2.2.0 · API 2 · 2026-10-18

### Quick
The default file is now walker-sim-with-wasm.js: big runs use the WebAssembly walking loop first (about 1.5 times faster in Chromium and Firefox), and the JavaScript loop when WebAssembly is not usable. Same counts either way. In WebKitGTK and GNOME Web a fresh page is about 15% to 30% slower with it; set cfg.wasm = false or copy walker-sim.js there.

### Deep
New default file walker-sim-with-wasm.js (66418 bytes; minified 34764, 13864 gzipped): walker-sim.js followed by walker-sim-wasm.js, built by test/make-min.js, so the WebAssembly walking loop is on from the start (it takes over after cfg.wasmAfter = 20,000 walkers; cfg.wasm = false switches it off; sim.engine says which loop ran). Same counts for the same seed. walker-sim.js (61220 bytes) and walker-sim-wasm.js stay. 1,000,000 walkers on the README network in a freshly opened page, graph building and start-up included, plain file to default file (lower is better): ungoogled-chromium 155.0.8059.39-1 88.6 ms to 57.6 ms (1.54x); Firefox 158.0 88.0 ms to 56.0 ms (1.57x); WebKitGTK 2.52.6 46.0 ms to 59.0 ms (0.78x); GNOME Web 46.5 50.0 ms to 58.0 ms (0.86x). In WebKitGTK and GNOME Web the WebAssembly loop is slower in a fresh page at every size tried (whole page, ms, plain / default / default with cfg.wasm = false): WebKitGTK 100,000 walkers 14 / 22 / 18, 1,000,000 46 / 53 / 47, 4,000,000 142 / 160 / 144; GNOME Web 15 / 25 / 19, 51 / 59 / 51, 144 / 173 / 156. The 2.1.0 gain figures for those two browsers came from a warmed-up page. Cost: default file 66418 bytes against 61220 for the plain one.

## 2.1.0 · API 2 · 2026-10-17

### Quick
Faster, with the same answers: a million walkers run about 2.3 times faster in the test browsers.

### Deep
Faster, same answers: for the same seed every count, step total and cost equals what 2.0.0 gave (2,000 random set-ups compared in full, plus 4 pinned tests). The main loop now picks each step's way on from a small lookup table instead of scanning, and the random numbers for costs, waits and uncertain weights are prepared once instead of at every draw. One million walkers on the example network: 192 ms to 80 ms in Node 22 (2.4 times faster), 238 to 102 in ungoogled Chromium 155 (2.3 times), 381 to 115 in Firefox 158 (3.3 times), 141 to 62 in WebKitGTK 2.52.6 (2.3 times), 139 to 53 in GNOME Web 46.5 (2.6 times). Uncertain weights are 1.2 to 1.8 times faster, random costs and waits 1.0 to 1.4 times (Gamma and Weibull costs barely change: 1.03 times). New: sensitivity() tells, for every link, how far each end's odds move per unit of weight, exactly and for all 501 links of the example network in about 2 to 3 ms (re-solving each link would take 0.7 to 2.7 s); with linkWeight it also gives the spread of every end's odds that the weight uncertainty causes in about 2 ms, where the simulation needs about 850 ms (within 7% of 300 exact re-solves). New and optional: walker-sim-wasm.js (3,968 bytes minified, 2,039 gzipped) runs the walking loop as a 1 KB WebAssembly program for big runs (it switches on after 20,000 walkers, only for fixed weights, one start item and no costs or waits): 1,000,000 walkers 110 ms to 52 ms in ungoogled Chromium 155 (2.1 times), 111 to 52 in Firefox 158 (2.1 times), 80 to 44 in Node (1.8 times), 82 to 65 in WebKitGTK 2.52.6 (1.3 times), no gain in GNOME Web 46.5; same counts; does nothing on a page that forbids WebAssembly (the page must allow wasm-unsafe-eval to use it); walker-sim-with-wasm.min.js joins both (34,807 bytes) for single-file apps. Bigger: walker-sim.min.js grows from 26,541 to 30,839 bytes (10.6 to 12.1 KB gzipped). 84 checks, 14 more than the 70 before.

## 2.0.0 · API 2 · 2026-10-17

### Quick
The random-number menu moved to an optional file, and very large runs (over 100,000 walkers) give different counts for the same seed. Smaller runs are exactly the same.

### Deep
Why API 2: the random-number menu (DISTS and DIST_BY) moved to the optional walker-sim-menu.js, so code that reads them must now load that file; and for runs above 100,000 walkers the same seed no longer gives the same counts (1.0.0 drew its sample thinning from the walkers' own random numbers). Up to 100,000 walkers the counts are exactly the same as 1.0.0 (checked at 1,000, 50,000 and 100,000 walkers, with the uniform and softmax rules, Poisson arrivals and uncertain weights); at 200,000 walkers they differ by up to 210 walkers (0.105 points), at 1,000,000 by up to 597 (0.06 points). Fixed: an item whose ways on all weigh 0 now stops its walkers, as the exact solver says. Before, they moved on at random: on a test network 24.8% reached each of two ends and 0% were stuck, where the exact answer is 0%, 0% and 50% stuck; now 49.8% are stuck. The exact solver no longer stops silently after 500 rounds: a loop that needs more is solved directly, and every exact result says converged, error and method. On a 2,000-item network with 10% loops 1.0.0 reported 0.02% of walkers reaching an end, where the truth is 100%; now it gives 100.000% in 0.4 s. A loop with no way out is reported as stuck. Faster: the main loop is about 1.7 times faster (1,000,000 walkers: 301 ms to 164 ms in Node, 343 to 204 in Chromium 155, 473 to 314 in Firefox 158, 275 to 128 in WebKitGTK 2.52.6). snapshot() on 100,000 walkers takes 0.13 ms instead of 13 ms in Node (about 100 times; 10 to 25 ms down to under 1 ms in the browsers) and now covers every walker's step count, not a sample of 100,000. The what-if sweep starts from the answer for the full network: 40 items 23.9 ms to 12.8 ms and 40 links 22.4 ms to 9.2 ms in Node (1.9 and 2.4 times; 1.2 to 3.8 times in the browsers). exactEndpoints on the small test network takes 0.77 ms instead of 0.60 ms (about 0.2 ms more, because it now also works out steps and cost). New: share a run between threads with firstTrial, export() and merge(): the counts come out identical to one run, and 2,000,000 walkers took 474 ms on one thread and 246 ms on 2 workers in Chromium (589 to 346 in Firefox, 244 to 151 in WebKitGTK) on a 4-core machine. The precision option stops a run once the widest 95% range is within a chosen size: on the example network 13,600 walkers (15 ms) instead of 1,000,000 (161 ms) for plus or minus 0.5 points. exactEndpoints gives meanSteps and meanCost to compare the simulation's step and cost numbers with. The curious rule is now documented and tested. Smaller: walker-sim.min.js is 26,541 bytes (10.2 KB gzipped) against 38,762 bytes (12.3 KB) for the 1.0.0 file, 32% smaller; moving the menu texts out saves 2,905 bytes minified (968 gzipped, about 14% and 11%) for scripts that do not need them. The readable file grew from 38,762 to 51,391 bytes and the minified core from 18.6 KB to 26.5 KB for the new features. 70 checks, 24 more than the 46 before.

## 1.0.0 · API 1 · 2026-10-17

### Quick
New module: sends random walkers through a network and reports where they end, how many steps and what it cost, with a 95% range on every result.

### Deep
New module, cut from Netflow Map's simulator. It sends random walkers through a network and reports where they end, how many steps and what it cost, with a 95% range on every result and the exact odds beside them for checking. Runs are repeatable from a seed, however they are cut into batches. Measured in Node on a network of 199 items and 561 links: 100,000 walkers in 57 ms (about 1.75 million a second), and the worst gap to the exact odds fell from 1.74 percentage points at 1,000 walkers to 0.12 at 100,000. New compared with the Netflow Map original, which was built into the app: `graph` turns a plain list of `{ from, to, weight }` links into the network (an unknown start item is a plain-words error), and the exact solver and what-if sweep run without the app around them. 16 kinds of random number are included.
