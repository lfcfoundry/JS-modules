# memory-compression-jso changelog

What changed in each version, newest first, in plain words. The numbers are explained in [tools/versions/README.md](../../tools/versions/README.md): the API number goes up only when someone using an older copy could be affected.

## 1.2.0 · API 1 · 2026-10-17
New: dates and times as text become one number. A column of ISO dates (2025-03-05T04:15:00Z, with milliseconds, date only, or with a space) is stored as one number per row instead of six and comes back as the same text; a row that is not a real date keeps the old way. Files are smaller (smaller is better): 20,000 sorted log timestamps 20.4 KB to 15.9 KB (22% smaller), 20,000 random dates 51.9 KB to 35.8 KB (31% smaller), 50,000 random dates and times 241.5 KB to 181.2 KB (25% smaller). A steady one-per-hour column stays at about 87 KB (0% change). Unpacking 20,000 sorted timestamps is faster in Firefox 158.0 (2.7 ms to 1.4 ms) and ungoogled Chromium 155 (1.6 ms to 1.3 ms) but slower in WebKitGTK 2.52.6 (2.3 ms to 3.6 ms) and GNOME Web 46.5 (2.5 ms to 3.3 ms); packing in WebKitGTK is 1.15 to 1.5 times faster (6.9 ms to 6.0 ms). A date column is used only when one number is expected to cost no more than the separate ones.
New: number-column arrays are reused between packs (at most 48 MB kept; pack(x, {pool: false}) turns it off, freeBuffers() empties it). Measured: 300,000 links pack about 1 to 6% faster in Node (85.0 ms to 79.6 ms, median of 41 alternating runs); no other set moved by more than the noise of about 5%.
New: fsst: true (off by default). A text column of short, varied strings (names, paths, log lines) is stored as FSST codes: a table of up to 255 learned text pieces plus a few bytes per string, instead of the joined text. Files are smaller (smaller is better): 20,000 names and cities 180.5 KB to 89.3 KB (51% smaller), invented words 119.4 KB to 56.8 KB (52%), file paths 247.1 KB to 110.3 KB (55%), log messages 234.5 KB to 153.9 KB (34%), 100,000 names and cities 902.0 KB to 423.8 KB (53%). Any one string can be read alone: view() keeps such a column at about a third of its restored size (555 KB to 166 KB for 20,000 names, 2,777 KB to 810 KB for 100,000, 3.3 to 3.4 times less) and opening a view plus reading the first field takes 0.53 ms instead of 4.75 ms in Firefox (9 times faster; 1.5 to 2.7 times faster in the other three browsers and Node); one string read takes 0.15 to 0.55 microseconds. Cost: packing is 1.9 to 6.4 times slower (about 14 to 24 ms against 2 to 8 ms for 20,000 rows) and unpacking the whole column is 1.0 to 1.6 times slower. Each text column is tried both ways and the smaller is kept, so patterns, small dictionaries and repeating whole values keep their own way. A 3 KB WebAssembly helper does the text-to-codes work from 4,096 rows: packing 1.2 to 1.8 times faster (18.3 ms against 28.7 ms in Firefox), unpacking 1.2 to 3.2 times faster (8.4 ms against 26.5 ms for 100,000 names in Chromium); plain JavaScript writes the same bytes.
New: Pcodec number columns through a separate optional file, memory-compression-jso-pco.js (441 KB, the 327 KB Pcodec 1.0.4 program is inside as text; Apache-2.0 notice in pco/NOTICE-pco.txt). Pass the object from MemoryCompressionJSOPco.load() as the pco option: each number column of 4,096 values or more is also tried with Pcodec and the smaller is kept, one byte in the file says which. Files are smaller (smaller is better): 100,000 sensor-style rows 1,537.3 KB to 508.5 KB (67% smaller), price ticks 289.1 KB to 154.2 KB (47%), random coordinates 1,677.6 KB to 1,200.2 KB (28%), 100,000 log events 837.0 KB to 638.4 KB (24%), 20,000 map features 1,803.5 KB to 1,362.8 KB (24%), 100,000 links 2,640.2 KB to 2,207.6 KB (16%), 20,000 user records 308.2 KB to 276.2 KB (10%), 50,000 scene items 1,077.6 KB to 1,035.4 KB (4%); a column of a repeating block of values stays the old way. Cost: packing is 1.2 to 3.5 times slower; unpacking ranges from 2.3 times faster (sensor rows in GNOME Web, 27 ms to 12 ms) to 1.8 times slower (log events in Chromium, 9.2 ms to 16.7 ms); starting the add-on takes 5.6 to 11 ms. A file that used Pcodec needs the add-on to open and says so in its error message when it is missing; any other file opens without it. Off unless the option is passed; a page that never loads the add-on is unchanged.
Files with a date, FSST or Pcodec column are format 3: 1.1.x refuses them with a clear message; files without one are unchanged (format 2). Format 3 files are read by this version, which also reads formats 1 and 2.
Not built, with the number: folding the repeated-text lookup into the splitting pass saves about 2 ms of an 85 ms pack in isolation (2%), below the noise. Not changed: sizes of number-only sets without the add-on, the plain way of packing text.
Built for a later per-column picker: every column already says which method stored it (plain, date, FSST, Pcodec) and the writer keeps the smallest, so another method can be added as one more column type.

Tested in: Node 22.22.0 (31 checks with and without WebAssembly, and the long random test); Firefox 158.0 (reports 158.0b5), ungoogled-chromium 155.0.8059.39-1, WebKitGTK 2.52.6, GNOME Web 46.5, one at a time, a fresh page for each data set; not run: a phone, a real Netflow Map scene

## 1.1.1 · API 1 · 2026-10-17
Packing a text column in WebKit is about 0.8 to 1.6 ms faster per pack (smaller is better) because a shortcut that cost time there was removed; no change in V8 (Chromium, Node), same bytes written, same file size. The README figures were refreshed (msgpackr in WebKit: 1.5 to 2.4 times slower, was 1.7 to 2.3).

Tested in: Node 22; Firefox 158.0 (reports 158.0b5), ungoogled-chromium 155.0.8059.39-1, WebKitGTK 2.52.6, GNOME Web 46.5 (research thread's runs of 1.1.0 build, same bytes)

## 1.1.0 · API 1 · 2026-10-17
New: text patterns. Strings that follow a pattern ('user7@example.org', '2025-03-05T04:15:00Z', 'Item 12 flow') are stored as the pattern once plus a column of numbers. Files are smaller: 50,000 user records 1.080 MB to 0.764 MB (29% smaller), 200,000 log events 2.481 MB to 1.670 MB (33% smaller), 100,000 scene items 2.652 MB to 2.099 MB (21% smaller); number-only sets such as the 300,000 links stay at 7.854 MB. Small mode packs the events 1.5 times faster (174 ms to 117 ms, Node). In a browser the extra step makes text-heavy packing about 1 to 4 ms slower at 10,000 to 40,000 rows (for example 6.3 ms to 7.7 ms in Firefox 158.0); pack(x, {patterns: false}) skips it and gives the old speed back.
New: shared objects stored by column. With refs: true, 100,000 items and 300,000 links that point at the item objects come out at 2.49 MB instead of 5.78 MB (2.3 times smaller) and pack in 228 ms instead of 484 ms (2.1 times faster); unpack 122 ms instead of 166 ms. msgpackr with its structure-clone option needs 11.49 MB for the same graph.
New: view() opens without restoring anything. Opening a view of 300,000 links takes about 0.06 ms instead of about 29 ms; a column is restored the first time it is read (one column of the links, about 1.4 ms), and the new loaded(), memory() and release() calls show and free the restored columns. An open view holds the packed 7.5 MB until a column is read (the live objects take 116 MB). Files made by 1.0.0 still open, restored all at once as before.
New: float32: true (off by default, lossy). Columns of fractions are kept in 4 bytes per value instead of 8: the 300,000 links go from 7.85 MB to 5.57 MB (29% smaller), worst relative error 6.0e-8.
New: patterns: false option, described above.
Faster with WebAssembly: a 608-byte helper reads big text columns (4,096 rows and up); the plain-JavaScript loop gives the same bytes. Pack, fast mode, WebAssembly on against off, Node: 300,000 links 83 ms against 112 ms; small mode 227 ms against 353 ms.
File format 2: a table of column sizes lets a view find one column without reading the others. A 1.1.0 file cannot be read by 1.0.0 (older files are read by 1.1.0, checked with a stored 1.0.0 file).
Not changed: the exact-restore rule, the sizes of number-only sets, irregular data (still 37% of the JSON text). Browsers: WebKit (WebKitGTK 2.52.6, GNOME Web 46.5) still packs text-heavy sets 1.7 to 2.3 times slower than msgpackr with records; not fixed.

Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1, WebKitGTK 2.52.6 and GNOME Web (Epiphany) 46.5, one at a time: the comparison page and the demo page; Node 22.22.0: 26 checks with and without WebAssembly plus the long random test. Not run: a phone

## 1.0.0 · API 1 · 2026-10-17
New module. It keeps a big list of plain JavaScript objects packed in memory and brings every value back exactly (numbers including NaN and -0, text, booleans, null, undefined, BigInt, Date, Map, Set, RegExp, typed arrays and nested objects; shared objects and cycles with refs: true). Arrays of 16 or more objects are stored by column, so key names are written once and the numbers go through memory-compression's float-aware packing. In Node 22.22.0, 300,000 link objects (57.3 MB of JSON text) become 7.9 MB (13.7%) in about 126 ms and unpack in about 84 ms; msgpackr with records makes 20.0 MB (34.9%) in 130 ms and unpacks in 139 ms. Over 7 data sets, fast mode is 1.5 to 5.3 times smaller than msgpackr with records and packs and unpacks within 10% of it or faster on 6 of 7 (50,000 user records are the exception: 1.7 and 1.4 times slower); small mode is another 15 to 36% smaller. Kept packed, 100,000 scene items take 2.5 MB instead of 55.8 MB of live objects (22 times less), and view() reads single items (about 0.5 microseconds each) or whole columns without making the other objects. Weak spots: data where every item is different (37% of the JSON text, speed about even with msgpackr) and WebKitGTK, where packing was 1.1 to 2.3 times slower than msgpackr with records on 6 of 7 sets.

Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1 and WebKitGTK 2.52.6, one at a time (2026-10-17): the comparison page against the other libraries (7 data sets, every result restored and compared value for value) and the demo page; GNOME Web (Epiphany) 46.5: the demo page. Node 22.22.0: 20 checks with and without WebAssembly and the long random test (4,000 cases). Not run: the comparison page in GNOME Web, a phone, a real Net Flow Map scene.
