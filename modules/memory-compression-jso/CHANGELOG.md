# memory-compression-jso changelog

What changed in each version, newest first, in plain words. The numbers are explained in [tools/versions/README.md](../../tools/versions/README.md): the API number goes up only when someone using an older copy could be affected.

## 1.1.0 · API 1 · 2026-10-17
New: text patterns. Strings that follow a pattern ('user7@example.org', '2025-03-05T04:15:00Z', 'Item 12 flow') are stored as the pattern once plus a column of numbers. Files are smaller: 50,000 user records 1.080 MB to 0.764 MB (29% smaller), 200,000 log events 2.481 MB to 1.670 MB (33% smaller), 100,000 scene items 2.652 MB to 2.099 MB (21% smaller); number-only sets such as the 300,000 links stay at 7.854 MB. Small mode packs the events 1.5 times faster (174 ms to 117 ms, Node). In a browser the extra step makes text-heavy packing about 1 to 4 ms slower at 10,000 to 40,000 rows (for example 6.3 ms to 7.7 ms in Firefox 158.0); pack(x, {patterns: false}) skips it and gives the old speed back.
New: shared objects stored by column. With refs: true, 100,000 items and 300,000 links that point at the item objects come out at 2.49 MB instead of 5.78 MB (2.3 times smaller) and pack in 228 ms instead of 484 ms (2.1 times faster); unpack 122 ms instead of 166 ms. msgpackr with its structure-clone option needs 11.49 MB for the same graph.
New: view() opens without restoring anything. Opening a view of 300,000 links takes about 0.06 ms instead of about 29 ms; a column is restored the first time it is read (one column of the links, about 1.4 ms), and the new loaded(), memory() and release() calls show and free the restored columns. An open view holds the packed 7.5 MB until a column is read (the live objects take 116 MB). Files made by 1.0.0 still open, restored all at once as before.
New: float32: true (off by default, lossy). Columns of fractions are kept in 4 bytes per value instead of 8: the 300,000 links go from 7.85 MB to 5.57 MB (29% smaller), worst relative error 6.0e-8.
New: patterns: false option, described above.
Faster with WebAssembly: a 608-byte helper reads big text columns (4,096 rows and up); the plain-JavaScript loop gives the same bytes. Pack, fast mode, WebAssembly on against off, Node: 300,000 links 83 ms against 112 ms; small mode 227 ms against 353 ms.
File format 2: a table of column sizes lets a view find one column without reading the others. A 1.1.0 file cannot be read by 1.0.0 (older files are read by 1.1.0, checked with a stored 1.0.0 file).
Not changed: the exact-restore rule, the sizes of number-only sets, irregular data (still 37% of the JSON text). Browsers: WebKit (WebKitGTK 2.52.6, GNOME Web 46.5) still packs text-heavy sets 1.7 to 2.3 times slower than msgpackr with records; not fixed.

Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1, WebKitGTK 2.52.6 and GNOME Web (Epiphany) 46.5, one at a time: the comparison page and the demo page; Node 22.22.0: 26 checks with and without WebAssembly plus the long random test. Not run: a phone

## 1.0.0 · API 1 · 2026-10-17
New module. It keeps a big list of plain JavaScript objects packed in memory and brings every value back exactly (numbers including NaN and -0, text, booleans, null, undefined, BigInt, Date, Map, Set, RegExp, typed arrays and nested objects; shared objects and cycles with refs: true). Arrays of 16 or more objects are stored by column, so key names are written once and the numbers go through memory-compression's float-aware packing. In Node 22.22.0, 300,000 link objects (57.3 MB of JSON text) become 7.9 MB (13.7%) in about 126 ms and unpack in about 84 ms; msgpackr with records makes 20.0 MB (34.9%) in 130 ms and unpacks in 139 ms. Over 7 data sets, fast mode is 1.5 to 5.3 times smaller than msgpackr with records and packs and unpacks within 10% of it or faster on 6 of 7 (50,000 user records are the exception: 1.7 and 1.4 times slower); small mode is another 15 to 36% smaller. Kept packed, 100,000 scene items take 2.5 MB instead of 55.8 MB of live objects (22 times less), and view() reads single items (about 0.5 microseconds each) or whole columns without making the other objects. Weak spots: data where every item is different (37% of the JSON text, speed about even with msgpackr) and WebKitGTK, where packing was 1.1 to 2.3 times slower than msgpackr with records on 6 of 7 sets.

Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1 and WebKitGTK 2.52.6, one at a time (2026-10-17): the comparison page against the other libraries (7 data sets, every result restored and compared value for value) and the demo page; GNOME Web (Epiphany) 46.5: the demo page. Node 22.22.0: 20 checks with and without WebAssembly and the long random test (4,000 cases). Not run: the comparison page in GNOME Web, a phone, a real Net Flow Map scene.
