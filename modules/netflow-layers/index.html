What it is and how it works

Lays out a graph in rows (a layered drawing), top to bottom or left to right. It is the layered engine behind Netflow Map's Flow, Top-down, Spine, Lanes, Arc and Matrix views. 19.3 KB gzipped (14.5 KB minified and gzipped).

  • Each page goes in a row, by fewest steps from the start or in story order.
  • Pages in each row are reordered to cut crossings, then placed.
  • Long links get stand-in stops or short tags; toSvg can draw the result.

Why it exists

Ordinary layered drawings make a mess of "going back" links and very long links in stories with thousands of pages. This engine has switches for exactly those maps.

Where it helps

  • Story and branching-narrative maps.
  • User-flow and page-journey diagrams.
  • Tall maps that should be cut into columns.

Not for: link labels, ports or curved routing around boxes.

How it compares

A small layered-graph drawer. It does less than ELK, and adds switches aimed at long story maps; ELK also wraps tall maps and bundles edges. With its default options (since 1.7.0) it draws fewer crossings than dagre and ELK on random maps of 400 and 1,000 items, in a small part of dagre's time (table below). ELK's speed and d3-dag: not measured.

Where it loses

  • Plain boxes only: link labels, ports and curved routing around boxes are not here (ELK has them).
  • Since 1.7.0 the default beats dagre and ELK on crossings but takes about 4 to 7 times as long as the old default (deep: false, rows: "route", which still draws 41 to 50% more crossings than both); still far under dagre.
  • Not measured: ELK's speed, and d3-dag's speed and crossings.
  • Story order is a choice, not the default: on a loop-free random map crossings rise from 90,351 to 131,569 (worse). Tags and bundling are the same kind of choice.
  • Brandes-Koepf straight-line placement was built, measured and left out: fewer slanted pieces but wider maps (4,223 to 49,496 px at 5,002 pages).

How to use it

Use

Copy netflow-layers.js.

One call, data only (items are made from the links and sized to their names):

svgElement.outerHTML = NetflowLayers.toSvg([{ from: "start", to: "a" }, { from: "start", to: "b" }, { from: "a", to: "b" }]);

The two steps:

var R = NetflowLayers.layout({
  root: "start",
  nodes: [{ id: "start", w: 140, h: 44 }, { id: "a", w: 140, h: 44 }, { id: "b", w: 140, h: 44 }],
  edges: [{ from: "start", to: "a" }, { from: "start", to: "b" }, { from: "a", to: "b" }, { from: "b", to: "start" }]
}, { dir: "TB", rows: "story", tagLen: 8 });
svgElement.innerHTML = NetflowLayers.toSvg(R);        // or draw R.nodes and R.edges yourself

Your input is never changed: the result holds copies of your nodes and links with the places added. Try it: demo.html (type links, the picture redraws). Test it: node modules/netflow-layers/test/run.js (19 checks, about 0.4 s).

Options

layout(graph, opts). Input: graph.nodes are { id, w, h } plus anything you like (label, choke: true for the must-pass pages, lane as a number); graph.edges are { from, to } (count optional); graph.root is the id where the story starts (without it, the first pages with no way in start the rows).

dir

"LR" (default, rows go left to right) or "TB" (rows go down).

rows

"best" (default since 1.7.0: lays out both ways below and keeps the one with fewer crossings; a tie keeps "route"), "route" (a page sits at its fewest steps from the start; the default before 1.7.0) or "story" (a page sits below every page that leads to it; only real loops go back).

tagLen

A number such as 8: links longer than this many rows become kind: "tag" (a stub and a name at each end), with no stand-in stops. 0 = off (default).

spine

true puts the nodes marked choke: true in one line.

better

true adds six more rounds of reordering and deepens from both the best and the usual result, so it never ends with more crossings than without it; about 1.1 to 1.9 times the time.

deep

Left out (default since 1.7.0): a lighter deeper search after the usual rounds (neighbor swaps after each row, at most 12 rounds, stops after 4 with no gain; 2 before 1.8.0).

Details

true: the full search (at most 80 rounds, stops after 4 with no gain). false: none (the default before 1.7.0). Never more crossings than without it. 1,000 random items: 33,763 crossings with deep: false, rows: "route", 21,166 by default (21,440 before 1.8.0) and with deep: true (dagre 23,965, ELK 22,602), in about 17, 112 to 118 and 114 to 122 ms in 3 cloud browsers. At 400 items the default is quicker than deep: true (34 to 38 against 44 to 51 ms) with the same 5,103 crossings. Maps over 20,000 stops skip it; orderRounds: 0 skips both the search and the second row choice.

orderRounds

A number: rounds of the usual order search (default 6, or 2 on maps over 600 stops). 0 keeps the first order, for a caller such as netflow-sankey that reorders anyway.

bundle

true lets links that start at the same page share one run of stand-in stops, and links that end at the same page and are alone at their start share one run from the end upward.

Details

Fewer stops and crossings on maps without tags; about the same where tags already removed the long links.

wrap

true (with dir: "TB") cuts a map more than 2.2 times taller than wide into columns side by side; links between columns become tags.

lanes

true puts nodes with the same lane number in their own band.

prev

{ id: 0-1 order from the last drawing } keeps the order stable.

spread

"wide" gives a looser, more tree-like drawing for wide screens: boxes beside each other get 2.4 times the gap top to bottom (1.4 times left to right), rows are 1.7 times further apart left to right (same top to bottom), and a box that leads to several boxes sits over the middle of them instead of over their weighted average.

Details

"tight" or nothing is the older, compact drawing exactly.

gapNode, gapLayer, maxVertices

Spacing, and the stop limit (default 90,000 stand-in stops, then it throws with tooBig: true).

All the switches are off by default; with everything off the drawing is exactly Netflow Map's older one (15 checks, 8 pinned fingerprints made by the app's own engine).

Returns { nodes, edges, pos, order, lanes, width, height, crossings, rows, ruler, info, dir }:

  • nodes: yours with x, y (top left) and layer (row number) added; pos is the same by id.
  • edges: yours with kind (fwd, back, flat = same row, self, tag) and pts (the stand-in stops of a long link, each [x, y]). A tag has tagFwd (true when it goes on down the page) and no pts.
  • info: { rows, columns, stops, back, flat, tags, goldTags, rowMode }. ruler: for each row { at, edge } (where to write "step 12" and where its column starts).

toSvg(result, colors) draws boxes, curves and tag chips as a plain SVG string (text is escaped); taper: true draws forward links as shapes that narrow from 5 px to 1 px, so direction shows without arrowheads.

Who uses it

Used right now in Netflow Map (its repository is private, so there is no link). Checked in each app's shipped file on its main branch on 2026.10.29. The module's own page is demo.html in this folder.

Good to know

What it is not

  • Plain boxes only: you give each node's size; no link labels, ports or curved routing around boxes.
  • Rows are by fewest steps from root unless rows: "story".
  • More than 90,000 stand-in stops (page boxes plus the stops long links need) throws; turn on tagLen first.

More

WebAssembly (1.5.0)

The row-order search (crossing counts, sweeps, neighbor swaps) and the row placement run in WebAssembly, built from wasm/order.c (sh wasm/build.sh, then python3 wasm/embed.py puts the 10,909 bytes into netflow-layers.js as base64). A page needs only 'wasm-unsafe-eval' in script-src; nothing is fetched. The pictures are the same to the last digit as the plain JavaScript, which stays in the file as the fallback (no WebAssembly, blocked by the page rule, a map under 100 stops, or a failed call). NetflowLayers.wasm is { on, min, calls, error }: set on = false to force JavaScript, min to change the 100-stop limit, read calls and error to see what happened. Measured in ungoogled Chromium 155, Firefox 158 and WebKitGTK 2.52.6, 5,000 pages (lower is better): 37.7 to 26.9, 55 to 41 and 53 to 43 ms with wasm off and on; 1,000 pages 6.65 to 4.8, 10 to 8 and 8.5 to 7 ms. The first map of 100 stops or more compiles the module once (about 4 ms in WebKitGTK, under 1 ms in Chromium).

Credits

  • The layered ("Sugiyama-style") way of drawing a graph in rows: rows first, then an order inside each row to cut crossings, then places. Idea only, no code. The same steps are in Eclipse ELK (EPL license; its overview was read, its code was not), dagre and d3-dag.
  • Ideas read about in ELK's documentation and papers and written fresh here: wrapping a tall map into columns (ELK calls it edge wrapping and layer unzipping) and letting links that share a page share their stops (bundling, also in a Microsoft Research paper on layered drawings with edge bundling). Idea only, no code.
  • Tapered links (narrow from the source to the target, so direction shows without arrowheads) follow the idea of Holten and van Wijk; the research notes mark that study as not re-read, so treat the credit as a pointer.
  • Brandes-Koepf placement (a published method) was tried in the research, measured and not included; none of its code is in this module.
  • The crossing counter is a standard Fenwick-tree (binary indexed tree) count. Textbook technique, no code from others.
  • The engine was cut from Netflow Map (LFC Foundry's own code).

No code from others; the ideas above are theirs.
