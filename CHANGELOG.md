- 2026-10-17 · **zip-open** 1.1.0 · API 1: The checksum check on every unpacked file is about 3.9 times faster: 2.97 to 0.76 ms per MB in Node 22.22, 2.89 to 0.74 in ungoogled Chromium 155 (3.9 times), 3.25 to 0.85 in Firefox 158 (3.8 times), 2.7 to 0.7 in WebKitGTK 2.52.6 and in GNOME Web 46.5 (3.9 times), measured on 20 MB (best of 3). At the 400 MB size limit that is about 1.2 s down to 0.3 s. It uses the 'slicing by 8' method (eight table lookups per eight bytes, reading whole words when the bytes sit on a 4-byte boundary). The answers are exactly the same: 814 checksums (every length 0 to 89 at every start position 0 to 8, 1 MB and 20 MB buffers, the standard test value) gave 0 different from a plain CRC, in Node and in all four browsers. The file grows by about 1.3 KB (26,143 to 27,468 bytes). Nothing else in the module changed. Tested in: Node 22.22.0 module test (15 checks passed) and tests/zip-open-crc-browser.js, one browser at a time: ungoogled Chromium 155.0.8059.39-1, Firefox 158.0 (reports 158.0b5), WebKitGTK 2.52.6 and GNOME Web (Epiphany) 46.5, each giving the same 814 checksums as a plain bit-by-bit CRC (0 different). Not run: a phone.
- 2026-10-17 · **zip-open** 1.0.0 · API 1: New module, cut from Net Flow Map's file opener. It opens .zip and Excel .xlsx files in the browser or in Node, with no libraries: text files come out as text, every sheet comes out as a CSV table, and every problem is a plain-words note. Every limit is counted on the bytes that really come out, not on the sizes the zip claims. Measured in Node on a zip of 1 GB of zeros (0.97 MB on disk) whose header says 1,000 bytes: this module refuses it in about 0.05 s using about 47 MB, while fflate 0.8.3 took 3.8 s and returned a 1,000-byte file with no error. New compared with the Net Flow Map original: `read(bytes, entry, limit)` for files that are not text, and a `textExt` option to choose which file endings count as text (before, the list was fixed). The Excel reader is bundled inside, so there is nothing else to include. 14 checks, about 2.6 s. Tested in: Node checks; the demo page in Firefox 158, ungoogled Chromium 155 and WebKitGTK 2.52.6, one at a time (`tests/flow-demos.js`, 2026-10-17; WebKitGTK 2.52.6 through `tools/webkit-driver`). Not run: GNOME Web (Epiphany) 46.5, a phone.

Fixed: an item whose ways on all weigh 0 now stops its walkers, as the exact solver says. Before, they moved on at random: on a test network 24.8% reached each of two ends and 0% were stuck, where the exact answer is 0%, 0% and 50% stuck; now 49.8% are stuck. The exact solver no longer stops silently after 500 rounds: a loop that needs more is solved directly, and every exact result says converged, error and method. On a 2,000-item network with 10% loops 1.0.0 reported 0.02% of walkers reaching an end, where the truth is 100%; now it gives 100.000% in 0.4 s. A loop with no way out is reported as stuck. Faster: the main loop is about 1.7 times faster (1,000,000 walkers: 301 ms to 164 ms in Node, 343 to 204 in Chromium 155, 473 to 314 in Firefox 158, 275 to 128 in WebKitGTK 2.52.6). snapshot() on 100,000 walkers takes 0.13 ms instead of 13 ms in Node (about 100 times; 10 to 25 ms down to under 1 ms in the browsers) and now covers every walker's step count, not a sample of 100,000. The readable file grew from 38,762 to 51,391 bytes and the minified core from 18.6 KB to 26.5 KB for the new features. 70 checks, 24 more than the 46 before.
