## Changes since labels began

- 2026-10-17 · **zip-open** 1.0.0 · API 1: New module, cut from Net Flow Map's file opener. It opens .zip and Excel .xlsx files in the browser or in Node, with no libraries: text files come out as text, every sheet comes out as a CSV table, and every problem is a plain-words note. Every limit is counted on the bytes that really come out, not on the sizes the zip claims. Measured in Node on a zip of 1 GB of zeros (0.97 MB on disk) whose header says 1,000 bytes: this module refuses it in about 0.05 s using about 47 MB, while fflate 0.8.3 took 3.8 s and returned a 1,000-byte file with no error. New compared with the Net Flow Map original: `read(bytes, entry, limit)` for files that are not text, and a `textExt` option to choose which file endings count as text (before, the list was fixed). The Excel reader is bundled inside, so there is nothing else to include. 14 checks, about 2.6 s. Tested in: Node checks; the demo page in Firefox 158, ungoogled Chromium 155 and WebKitGTK 2.52.6, one at a time (`tests/flow-demos.js`, 2026-10-17; WebKitGTK 2.52.6 through `tools/webkit-driver`). Not run: GNOME Web (Epiphany) 46.5, a phone.
- 2026-10-17 · **webkit-driver** 1.1.0 · API 1: Stray processes: killing a test run with SIGTERM or Ctrl-C used to leave 7 processes behind (virtual screen, message bus, driver, browser); now 0 are left (measured in WebKitGTK 2.52.6). Clicks are faster: 20 to 22 ms before, 16.6 to 17.8 ms when the pointer moves (about 17% faster) and 5.8 to 7.6 ms when it is already there (about 70% faster), because press and release now travel in one call. waitForFunction now checks inside the page every frame instead of every 50 ms from Node, so a condition that becomes true after 120 ms was seen after 162 to 164 ms and now after 130 ms; a condition that throws now rejects instead of hanging until the timeout. New launch options (all off by default): deviceScaleFactor (whole numbers; the page sees devicePixelRatio 2 with the same page area), colorScheme: 'dark' and reducedMotion: true (the matching media queries become true), and serve (loads your files through a small local web server so errors thrown while a page loads are reported with their real text; on a test page 2 of 2 load-time errors were caught, versus 0 of 2 from a file:// page). The file grew by 3,316 bytes (973 gzipped). Not measured: Net Flow Map's own 82-check suite with the patch. Tested in: WebKitGTK 2.52.6 (17 real checks and 7 pretend-driver checks pass; plus the five Apple Press piece checks, the four Net Flow Map demos and the idle-core same-answers run through tests/webkit-shim.js) and GNOME Web 46.5 (the real checks that apply to it pass). Not run: Firefox 158 and ungoogled Chromium 155 (this driver does not drive them) and Net Flow Map's own 82-check suite.

- 2026-10-17 · **walker-sim** 2.0.0 · API 2: Why API 2: the random-number menu (DISTS and DIST_BY) moved to the optional walker-sim-menu.js, so code that reads them must now load that file; and for runs above 100,000 walkers the same seed no longer gives the same counts (1.0.0 drew its sample thinning from the walkers' own random numbers). Up to 100,000 walkers the counts are exactly the same as 1.0.0 (checked at 1,000, 50,000 and 100,000 walkers, with the uniform and softmax rules, Poisson arrivals and uncertain weights); at 200,000 walkers they differ by up to 210 walkers (0.105 points), at 1,000,000 by up to 597 (0.06 points). Fixed: an item whose ways on all weigh 0 now stops its walkers, as the exact solver says. Before, they moved on at random: on a test network 24.8% reached each of two ends and 0% were stuck, where the exact answer is 0%, 0% and 50% stuck; now 49.8% are stuck. The exact solver no longer stops silently after 500 rounds: a loop that needs more is solved directly, and every exact result says converged, error and method. On a 2,000-item network with 10% loops 1.0.0 reported 0.02% of walkers reaching an end, where the truth is 100%; now it gives 100.000% in 0.4 s. A loop with no way out is reported as stuck. Faster: the main loop is about 1.7 times faster (1,000,000 walkers: 301 ms to 164 ms in Node, 343 to 204 in Chromium 155, 473 to 314 in Firefox 158, 275 to 128 in WebKitGTK 2.52.6). snapshot() on 100,000 walkers takes 0.13 ms instead of 13 ms in Node (about 100 times; 10 to 25 ms down to under 1 ms in the browsers) and now covers every walker's step count, not a sample of 100,000. The what-if sweep starts from the answer for the full network: 40 items 23.9 ms to 12.8 ms and 40 links 22.4 ms to 9.2 ms in Node (1.9 and 2.4 times; 1.2 to 3.8 times in the browsers). exactEndpoints on the small test network takes 0.77 ms instead of 0.60 ms (about 0.2 ms more, because it now also works out steps and cost). New: share a run between threads with firstTrial, export() and merge(): the counts come out identical to one run, and 2,000,000 walkers took 474 ms on one thread and 246 ms on 2 workers in Chromium (589 to 346 in Firefox, 244 to 151 in WebKitGTK) on a 4-core machine. The precision option stops a run once the widest 95% range is within a chosen size: on the example network 13,600 walkers (15 ms) instead of 1,000,000 (161 ms) for plus or minus 0.5 points. exactEndpoints gives meanSteps and meanCost to compare the simulation's step and cost numbers with. The curious rule is now documented and tested. Smaller: walker-sim.min.js is 26,541 bytes (10.2 KB gzipped) against 38,762 bytes (12.3 KB) for the 1.0.0 file, 32% smaller; moving the menu texts out saves 2,905 bytes minified (968 gzipped, about 14% and 11%) for scripts that do not need them. The readable file grew from 38,762 to 51,391 bytes and the minified core from 18.6 KB to 26.5 KB for the new features. 70 checks, 24 more than the 46 before. Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1, WebKitGTK 2.52.6 and GNOME Web 46.5, one at a time: the same-answers and timing run (tests/walker-sim-browser.js, readable and minified file; WebKit through tools/webkit-driver) and, in the first three, the demo page (tests/flow-demos.js); 70 Node checks in Node 22. Not run: the demo page in GNOME Web, a phone.

- 2026-10-17 · **memory-compression** 1.0.0 · API 1: New module. It keeps big arrays, coordinates, records and text packed in memory and brings them back exactly, bit for bit. Fast mode (a restore speed of about 0.7 to 1.1 GB/s with its WebAssembly helper, about 0.2 to 0.5 GB/s without it) makes records 39% of their size and walking floats 57%; small mode makes them 29% and 49% (fflate level 6: 46% and 74%; lz4js: 72% and 99.8%). A 120 MB scene restores in about 175 ms in fast mode (lz4js 525 ms, fflate 1.2 s, pako 1.6 s), and six such scenes took 375 MB of memory packed instead of 720 MB raw. Noisy float coordinates still only shrink 8% (fast) to 18% (small); the floats-aware pre-step is what gets small mode 8 to 25 percentage points under fflate on floats, and on text small mode is within 1 point of fflate and pako. view() restores a single 1 MiB piece of a packed array in about 1 to 2 ms, so a big array can stay packed and be read piece by piece. Measured against fflate, pako, lz4js, a WebAssembly LZ4 and a WebAssembly zstd in Node and in all three browsers: it is the smallest on floats and records (records 39% against 72% for the LZ4 packages and 49% for zstd level 3) and faster than all of them on records; the WebAssembly LZ4 restores faster on data that cannot shrink and in WebKitGTK, and zstd is smaller on text. It also reads and writes standard LZ4 blocks, deflate, zlib and gzip, readable by other tools. The WebAssembly helper is optional: where a page policy forbids it, everything still works about 1.5 to 4 times slower. Tested in: Firefox 158.0, ungoogled Chromium 155.0.8059.39-1 and WebKitGTK 2.52.6, one at a time: the full benchmark page (79 of 79 self-checks pass in each, every result restored byte for byte), a comparison page against fflate, pako, lz4js, lz4-wasm, zstd-wasm and CompressionStream, and the demo page; the demo page also in GNOME Web (Epiphany) 46.5 (both rows restored byte for byte at 8 MB and 32 MB); Node 22.22.0: 23 checks, with and without WebAssembly. Not run: the benchmark page in GNOME Web 46.5, a phone, a real Net Flow Map scene.
