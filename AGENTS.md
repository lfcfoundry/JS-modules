# Notes for AI assistants (and the humans working with them)

This repository is meant to be read, copied from and extended by people and AI helpers together.

## Using a module in someone else's project
1. Open `modules.json`, pick the module, read its `README.md` (the "Limits" section matters).
2. Copy the single `.js` file into the project (keep its MIT header). No install step, no dependencies.
3. Wire it up with the snippet at the top of the file or in the README, and open the module's `demo.html` to see it working.

**WebAssembly is allowed** (owner's policy from 2026-10-17): a page may add `'wasm-unsafe-eval'` to `script-src` and nothing else in its policy changes. **WebAssembly is the standard** (owner, 2026-10-18): heavy or hot code paths run in WebAssembly by default, with plain JavaScript as the fallback, and a new heavy module is built WebAssembly-first. Skip it only when browser numbers show no gain or a size limit rules it out. A module with a WebAssembly helper keeps its source, a rebuild step and a plain-JS fallback, ships the WebAssembly-first file as its default (`lzma-decode`, `ppmd-decode` and `walker-sim` name it `<module>-with-wasm.js`) and keeps the JavaScript-only file beside it for pages that must stay tiny.

## Changing this repository
- Keep every module **free of dependencies** and, where it makes sense, **one file** (`frame-kit` is four small files that each work alone). Use ES5-compatible syntax (`var`, no build step), with the UMD wrapper at the top level (browser global + `module.exports`).
- Never throw out of a probe or a save; return a safe fallback.
- Add or update a check for every behavior you change: `tests/run.js` for the original modules, or the module's own `test/` folder (run all of those with `npm run test:kits`).
- Keep the header on each file: `Copyright (c) 2026 LFC Foundry. MIT License`. Contributions are accepted under the same license.
- Every HTML page here (demos, examples, tools, the front page) starts, right after `<!doctype html>`, with the LFC Foundry header comment in `tools/foundry-header.txt` (put the page's title where `{NAME}` stands; no `--` inside it). The one visible credit is a small footer line, `Forged by LFC Foundry • MIT Licensed`, at the end of each demo and tool page (not on internal test pages). Packed examples get the header added after packing, so it stays readable at the top. Commits are still authored and committed by JNFoo.
- Do not add game art, characters, brand names or text from Apple Press. Do not add code you cannot license under MIT, and say where an idea came from in the module README ("Prior art and credits").
- The demo pages (`modules/*/demo.html`) share one look, the landing's design: `tools/theme/theme.css` is inlined between marker comments by `python3 tools/theme/apply-theme.py` (run it after adding a demo; `--check` says which pages are out of date; `--remove` takes it out). Full-window demos and a page with a strict security policy are left alone; the list is at the top of the script.
- Plain words in docs. Say what a thing does, then its limits.

## Version labels
Every module and tool has a label like `1.2.3 · API 1` (classic major.minor.patch, plus an API number that always equals the major). Patch = a fix, minor = a new option or feature that breaks nobody, major = something an existing user could trip over (an option removed or renamed, a result that now means something else). `modules.json` holds the label and `tools/versions/versions.py` copies it everywhere else; never edit the copies by hand. When you change a module's or tool's shipped code, run `python3 tools/versions/versions.py set <id> X.Y.Z --note "what changed, in plain words"` in the same commit; it updates the label everywhere and adds the entry to that module's `CHANGELOG.md`. Write the entry in plain words and quantify it: for every improvement say how much (how many milliseconds or percent faster, how many KB smaller, how many more cases caught) and in what test it was measured; for every new feature say plainly what it does and what the default is; for every fix say what went wrong before and what happens now. "Faster" or "better" alone is not enough. If a number was not measured, say that instead of guessing. Docs-only, test-only and example-only changes keep the label. `python3 tools/versions/versions.py check` must pass. See [tools/versions/README.md](tools/versions/README.md).

## Run the tests
`npm i playwright-core && CHROMIUM=/path/to/chrome node tests/run.js`

Test **only** with the browsers on the `browsers` branch of the private knowledge-base repository: **Firefox 158**, **ungoogled Chromium 155** and **WebKitGTK 2.52.6**, on Linux. GNOME Web is no longer a test browser. Read that branch's README before each test run, because versions may be updated and a browser may be added or removed; follow what it says then. Do not use Chromium 141 or 153 or Firefox 157 for new results. Run one browser at a time (two at once make timing flaky), point the tests at the install with `CHROMIUM`, `FIREFOX_PATH` and `GECKODRIVER_PATH` (WebKitGTK only through WebDriver), and label every result with the browser and version that ran. Say so when a browser or a real phone was not checked. Keep the browser files out of this repository.

**Every release records its browsers.** Run `versions.py set <id> X.Y.Z --tested "Firefox 158, ungoogled Chromium 155, WebKitGTK 2.52.6" --short "one plain line for users" --note "full entry with numbers"`: the `--tested` text becomes the **Tested in** line of the full changelog entry (private folder) and of the module's README. Name each browser with its version, say what was not run, and write "not recorded" only when it truly is not known. Left out, the line says "not recorded" and the command reminds you. If you test an older release later, `versions.py tested <id> X.Y.Z "..."` fixes that entry's line.

**Faster, trustworthy testing:** follow the universal QA and browser-testing guide at `build-notes/qa/QA-AND-BROWSER-TESTING-UNIVERSAL-GUIDE.md` in the private lfcfoundry/knowledge-base repo (print the real browser version on line 1 of every run; targeted checks while working; full run once when the design is final).

**Faster runs, each with an off switch.** `node tests/kits.js` runs independent steps side by side, slowest first, on up to 4 lanes (all browser steps share one lane, so two browsers never run at once), and ends with the total time, the time one-after-another would take, and the five slowest steps. A step that fails while others ran beside it is run once more alone; if it passes alone it is shown as `pass*` and its first output is kept in a log file. Switches: `--serial` (or `KITS_JOBS=1`) runs one step at a time as before; `--jobs N` sets the lanes; `KITS_RETRY=0` turns the second try off; `--quick` leaves out the browser steps; `--only REGEX` picks steps by name; `--list` shows what each step watches; `--changed [BASE]` runs only the steps whose files (or files they use) changed since BASE (default `origin/main`) and runs everything when it meets a file no step knows; `--all` turns `--changed` off. Use `--changed` while working and one plain `node tests/kits.js` when a design is final. The browser tests need `CHROMIUM=/path/to/chrome`, refuse to run without it, and print the real browser version first. Browser tests wait for the thing they need (a condition) instead of sleeping a fixed time; keep a real sleep only for real time, such as an animation or a timer the page itself runs. Running two pages of one browser at the same time was tried and hangs, so do not.

**Waits that were cut (2026-10-17), each with its switch.** The Apple Press piece checks open the demos with `#fast` (grown-ups-door: door stays open 0.5 s instead of 1.5 s; slow-note: quiet time 0.5 s instead of 1.5 s) and speed-lab's stubborn-card check uses `#tiny` steps of 120 ms; the defaults of every demo are unchanged. `tests/gif-writer-browser.js` and `tests/save-kit-speed-browser.js` time one run (three rounds for save-kit) when nothing is compared and the full best-of-3 and best-of-7 when `OLD=` is given. `modules/lzma-decode/test/run.js` keeps the reference streams from Python's xz in the temp folder under a hash of the input (`NO_FIXTURE_CACHE=1` turns that off). The lzma-pack and ppmd-pack key search counts byte pairs instead of trying 256 keys (6.9 s to 0.04 s on 190 KB, same key).

## Adding a module
1. Make `modules/<name>/` with the file(s), `README.md` (the version and **Tested in** lines at the top; then a few lines saying what it is and how it does it; then `## Why it exists` as the first section (owner's rule, 2026-10-18: this order for every README, tool and app); then, section by section, quick start, API, `## How it compares` with a table against the real alternatives, `## Prior art and credits` naming every piece of code, algorithm or idea taken from someone else with its license, limits, a "For AI agents" section), `CHANGELOG.md` (the short end-user one: one plain line per change; the full entry goes to `/mnt/project-files/changelogs-full/JS-modules/<id>.md` through `versions.py set`), `demo.html`, and a `test/` folder.
   - Speed numbers in a README or changelog come from the test browsers only, one at a time, with the browser and version next to each number and "smaller/lower is better" stated; Node is for pass/fail checks and byte counts. Where a number was not measured, write "not measured".
   - When you add or change a module that competes with existing libraries, benchmark those libraries in the test browsers for the release, not only your own before and after.
2. Add it to `modules.json` (with `short`, at most 100 characters, a `category` (one of the ids under `categories` in `modules.json`; modules, tools and story packages share the list); `file` is what gets measured for the size), then run `python3 tools/versions/versions.py sizes`: it writes the root README tables and the "All at a glance" index, and the sizes on the front page. Add it to `llms.txt` and `index.html` by hand (a line each), and to `tests/kits.js` if it has its own tests. `versions.py check` fails when a row has no size, the tables or the front page are stale, or a label disagrees.
3. Only add something that is not already well covered by open source, and say so honestly in the README. Where this repository already has something close, link it and say how they differ.

## Netflow Map engine updates
Owner's rule (2026-10-18): every significant update to the Netflow Map engine also ships here as a new version of `modules/netflow-engine`, separate from the Sankey, layout and network-map add-ons (`netflow-sankey`, `netflow-layers` and later ones) that plug into it. The engine runs without add-ons for the Network view and the arrangements; the story views need `netflow-layers`, and the Sankey view's look needs an add-on with `options`, `layout` and `apply`. The engine file is cut from Netflow Map's engine by a script, so never hand-edit it: each update arrives as a brief under `/mnt/project-files/js-modules-research/netflow-engine/` and is applied as a new version. `modules/netflow-engine/README.md` explains the add-on hand-over.

## Working with other sessions
Several AI sessions and people may push to this repository. Before you start, `git fetch` and read `TASKS.md`; put your row in it and push that small commit first. Rebase or merge on the latest `main` before you push, never force-push, and do not rewrite another session's files without saying so in the commit message.

## House-rule hooks

Run `sh tools/hooks/install.sh` once per clone (a Claude Code session does it for you through `.claude/settings.json`). `commit-msg` rejects a `Claude-Session:` line, a claude.ai link, any author or committer not on the allow-list in `tools/hooks/authors.txt` (it starts with JNFoo only; Claude is always refused) and a malformed version stamp; `pre-commit` repeats the author check, warns about British spellings and checks that new files carry the MIT header (HTML pages the LFC Foundry comment); `pre-push` applies the same message and author rules to every commit you are about to push, so a rebase or cherry-pick cannot slip past. They can still be skipped with `--no-verify` or by a clone that never ran the installer. See `tools/hooks/README.md`; run `sh tools/hooks/test.sh` after changing them.
