# B18b gate results: saving straight from row objects (2026.11.11, 11:43 PM Eastern)

From the thread "Research compression and data-performance techniques". Research only: nothing here is in `modules/lfc-pack` yet. The patch is `experiments/b18b-patch-rows-to-columns.py` on the JS-modules branch `claude/project-thread-8535qt`, in `docs/research/compression-2026-11-11/`.

## What B18b is
`packRows(rows)` today turns the rows into JSON text and then packs the text. B18b hands rows that are plain objects with scalar values straight to the column writer, in slices of about one block, so there is no JSON text step. Anything else (nested values, arrays, `toJSON`, NaN, -0, `exact`, `block`, `share`) takes today's path.

**Gate:** the row path is taken only when the rows would make more than 16 MB of text, or when fewer than 40% of the cells in the first 256 rows are strings, and only for more than 4,096 rows. Below that, files are byte-identical to 0.9.3. Why: string-heavy tables under 16 MB pack 1.1 to 1.5 times slower through the row path, because the wasm text scanner handles strings faster than the JavaScript column writer does. Above 16 MB, today's text path leaves the wasm scanner anyway.

**Size fix:** on the row path, the writer tries both number layouts (absolute and delta varints), as the fast wasm writer does. Without this, taxi files came out 1.1% bigger. With it, files are 0.999 to 1.000 of 0.9.3's size.

## Which baseline each number uses
- **This gate** compares lfc-pack **0.9.3** (main, which already has B3b and B14) with **0.9.3 + B18b**. So 0.51 to 0.90 is **B18b alone**, on top of what has already shipped.
- **The earlier Chromium stack table** (11:08 PM) compared everything with **0.8.3**. In it, "approved stack + B18b" was 0.29 to 0.72 of 0.8.3, and the approved stack alone was 0.78 to 1.07 of 0.8.3. Those numbers line up: approved + B18b divided by approved alone gives 0.37 to 0.67, inside or near this gate's B18b-alone range. The two runs differ in base (0.8.3 build plus the null plane against 0.9.3) and in the size fix, so expect a few points of drift.

## Correctness
- Every file in every browser read back to the same values. Values were compared with keys sorted.
- lfc-pack keeps keys in first-seen order per block (value-exact mode, as documented). B18b cuts blocks by row count rather than byte count, so a later block can list a key in another order. On 200,000 GitHub events with an often-missing key, 0.9.3 itself reorders keys on 53,388 rows and B18b on 31,164. Values are identical in both.
- Files under the gate are byte-identical to 0.9.3.

## Limits
- One shared 4-core cloud machine. No laptop, tablet or phone runs.
- Every cell uses 3 rounds, except the re-run.
- Nested rows were checked only as a fallback (events: about even).
