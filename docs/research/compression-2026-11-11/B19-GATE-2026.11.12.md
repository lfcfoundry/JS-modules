# B19 gate results: finding rows where key = value (2026.11.12, 12:03 AM Eastern)

From the thread "Research compression and data-performance techniques". Research only: nothing here is in `modules/lfc-pack` yet. The patches are on the JS-modules branch `claude/project-thread-8535qt`, in `docs/research/compression-2026-11-11/experiments/`:
- `b19-patch-equality-reads.py`
- `b19-patch-cache.py`

The idea came from the Codex review (KB M110).

## What B19 is
`unpack(file, { equals: { key, value }, keys? })` returns the rows whose value under `key` is `=== value`. A missing key never matches `null`. Today an app reads every row and then filters.

B19 does three things:
1. It tests the one column first and builds row objects only for the matches (the B14 trick, applied to equality). If more than half the rows of a block match, it takes the whole-block path.
2. For a dictionary (`D`) column, it decompresses the label list first. A block whose labels lack the value stops there, and no other column is decompressed.
3. With the opt-in cache, it keeps each block's decoded columns, plus one code per row for the asked key, between queries on the same file. That is the Codex variant, where its 71 to 10 ms came from.

## 3-browser results, as a share of today's read-then-filter (lfc-pack 0.9.3, 4 MB blocks, 3 fresh pages per cell)

24 queries in a row (6 to 3 different values, cycled), shown as Chromium 156 / Firefox 158 / WebKitGTK 2.52.6:

| Data | B19 | B19 + cache |
|---|---|---|
| GitHub events, 200,000 flat rows (real) | 0.69 / 0.72 / 0.79 | 0.28 / 0.21 / 0.27 |
| Orders, 100,000 | 0.63 / 0.63 / 0.59 | 0.24 / 0.23 / 0.21 |
| Logs, 300,000 | 0.53 / 0.55 / 0.64 | 0.12 / 0.10 / 0.13 |
| Taxi trips, 300,000 (real, nullable flag) | 0.64 / 0.61 / 0.54 | 0.37 / 0.36 / 0.35 |
| GitHub events, 100 rows (tiny) | 0.82 / 0.67 / 1.38 | 0.40 / 0.50 / 0.88 |

The first query on a fresh page:

| Data | B19 | B19 + cache |
|---|---|---|
| GitHub events 200k | 0.75 / 0.87 / 0.86 | 0.86 / 0.88 / 0.99 |
| Orders 100k | 0.79 / 0.86 / 0.69 | 0.81 / 0.81 / 0.75 |
| Logs 300k | 0.86 / 0.86 / 0.83 | 1.03 / 0.90 / 0.94 |
| Taxi 300k | 0.52 / 0.40 / 0.36 | 0.51 / 0.45 / 0.41 |

- On the 100-row file the whole read takes 1 to 5 ms, under the timer step of Firefox and WebKit (1 ms). Those cells are noise, so the WebKit 1.38 is not a loss.
- The cache makes the first query a little slower, by 0 to 0.17, because it copies frames out of the read buffer.

**Per query, warm, Chromium** (`results/eq-q-chromium.json`):

| Query | Without codes | With codes |
|---|---|---|
| Value present in 0.4 to 25% of rows | 0.63 to 0.85 | about the same |
| Value present in more than half the rows | 0.94 to 1.00 | 0.97 to 1.00 (whole-block path) |
| Value in no block | 0.10 to 0.27 | **0.02 to 0.05** |

The dictionary-code step never costs more than reading without codes, so B19 needs no gate.

**Memory of the cache** (Node, heap plus buffers kept after 24 queries on the 6 MB, 300,000-row log file): about 99 MB. Without the cache it keeps 6 MB, and holding all rows from a full read takes 85 MB. So the cache costs about what keeping every row in memory costs. That is why it is opt-in.

## Stacked with the null plane (B13; the research build also has B3b and B14), against 0.9.3's read-then-filter

| | B19 alone | Null plane alone | Expected if independent | Measured together |
|---|---|---|---|---|
| Orders, first query (C / F / W) | 0.79 / 0.86 / 0.69 | 0.75 / 0.57 / 0.64 | 0.59 / 0.49 / 0.44 | **0.44 / 0.38 / 0.37** |
| Taxi, first query | 0.52 / 0.40 / 0.36 | 0.99 / 0.95 / 0.99 | 0.51 / 0.38 / 0.36 | **0.41 / 0.33 / 0.32** |
| Orders, 24 queries with cache | 0.24 / 0.23 / 0.21 | 0.44 / 0.54 / 0.59 | 0.11 / 0.12 / 0.12 | 0.15 / 0.16 / 0.14 |

- **Better than the sum of its parts on a first query.** B19 decodes fewer columns, and the null plane makes the columns it does decode typed and cheaper.
- **With the cache, about even or a bit worse than the sum.** Once every column is decoded once and kept, the null plane's faster decoding matters less.

## Correctness
`experiments/eqverify.cjs` gives the same rows as `unpack(file).filter(...)`, with the same key order, on 792 checks: 378 without the cache and 396 with it, on 0.9.3 and on the null-plane build. The checks covered:
- accents, CJK, emoji, empty text and near-duplicate labels
- null against a missing key, and a number asked of a text column
- 256 KB, 4 MB and 13 MB blocks, with and without `keys`
- real GitHub events (data kept in scratch, not committed)

The match counts were identical across modes on every page in the 3 browsers.

## Limits
- One shared 4-core cloud machine, 3 rounds per cell.
- No laptop, tablet or phone runs.
- The cache has no size limit or eviction yet. Shipping it would need one, for example "drop the cache when the file object is dropped" (the prototype uses a WeakMap on the file bytes), plus an explicit `clear`.

## Ideas this opened (not yet tested)
- **B19b:** decode only the matching positions of `D` and bit-packed (`B`) columns instead of whole columns. For values in a few % of rows, that is most of what is left of the time.
- **B8 follow-up:** a per-block label summary in the footer would skip blocks without the value before reading them (a format change).
