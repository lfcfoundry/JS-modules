# LZ4 1.11 principles: local validation update — 2026-11-11

This preserves the pre-publication research snapshot. The reviewed candidate files and portable fixtures are now on this isolated handoff branch; see [README.md](README.md) and [SOURCE-MANIFEST.md](SOURCE-MANIFEST.md).

This report updates the [November 10 framework](PERFORMANCE-ENGINEERING-FRAMEWORK.md) with measurements and review evidence. No canonical source, candidate, dependency, or benchmark fixture inside a repository was changed. No LZ4 dependency is proposed. Upstream performance figures are **not** forecasts for LFCFoundry.

## Executive finding

The only new measured local effect is the cost and memory exposure of making private worker-transfer copies. An independent fake-worker probe verified the safety value of those copies for LFC-pack Buffer input; a Node-only micro-pilot measured copy time and observed RSS for 64 KiB, 1 MiB, and 8 MiB slices. This establishes **a cost**, not a throughput benefit or an adoption threshold. A two-worker LFC-pack read queued twelve private block copies, demonstrating that a worker-count limit is not a queued-byte or process-memory limit. No LFCFoundry optimization in this report has yet passed a controlled performance acceptance gate.

## Sources and version boundary

The [Phoronix article](https://www.phoronix.com/news/LZ4-1.11-Released) reports the 1.11 release and the separate CLI memory option. The [upstream v1.11.0 release notes](https://github.com/lz4/lz4/releases/tag/v1.11.0) describe new library multithreading, small-block state reuse, AArch64 decode gains, worker scaling on upstream hardware, and sequential checksum/I/O limits. The [tagged frame header, lines 2211–2387](https://github.com/lz4/lz4/blob/v1.11.0/lib/lz4frame.h#L2211-L2387) documents experimental `nbWorkers`, approximately twice the worker count of jobs in flight, usually 1 MiB jobs or a larger single block, lazy worker/context creation, delayed streaming output, default source copying, and `LZ4F_srcStableUntilFlush` lifetime requirements. Those are LZ4 1.11 facts. Separating job count from byte ceilings, owning transferred memory, staging less data, and measuring latency as well as throughput are general engineering lessons. The cited evidence does not establish a new SIMD implementation applicable to these projects; SIMD remains only a testable hypothesis.

## What was measured

The `buffer-transfer-review.cjs` probe intercepted `Worker.prototype.postMessage` while decoding fake LFC-pack fixtures. With 12 selected compressed blocks and two workers, each submitted Buffer-backed block was copied to an exact-sized private `ArrayBuffer`, transferred once, decoded correctly, and left the original pooled/sliced/offset/overlapping/SAB-backed caller view usable. The unchanged baseline attempted a pooled-Buffer transfer of caller backing storage and raised `Cannot transfer object of unsupported type`; it did not complete normally. This is correctness/ownership evidence. It does **not** measure worker throughput, p95 latency, peak real-file memory, or atomicity under concurrent SAB mutation.

`copy-cost-pilot.cjs` ran each size/mode in a fresh Node process with 100 warm-up operations and `--expose-gc`. It compared the candidate's private-copy expression with a zero-copy view alias. The alias is an unsafe ownership comparator, **not** a candidate replacement. Each single run samples `process.memoryUsage()` every ten iterations; observed peaks can miss short spikes and include runtime/GC effects. No confidence interval or end-to-end decode was measured.

| Input view | Repetitions | Alias microseconds/op | Private copy microseconds/op | Logical bytes copied by private mode | Private peak observed RSS | Alias peak observed RSS |
|---:|---:|---:|---:|---:|---:|---:|
| 64 KiB | 2,000 | 1.14 | 47.15 | 131.1 MB | 114.6 MB | 47.6 MB |
| 1 MiB | 400 | 1.98 | 634.85 | 419.4 MB | 184.4 MB | 48.1 MB |
| 8 MiB | 80 | 4.07 | 5,551.84 | 671.1 MB | 131.9 MB | 56.0 MB |

Interpretation: cost grows with bytes copied, and transient external allocations can raise observed RSS materially. Different repetition counts and GC schedules make peak RSS **non-comparable across size rows**. The changing alias/copy numbers do not establish a useful real-workload speedup from eliminating copies, because doing so would lose the demonstrated caller-memory safety. The pilot is a sizing signal for a proper pipeline benchmark.

## Memory and concurrency model to test

Keep six controls separate: maximum concurrent worker jobs, maximum queued jobs, maximum live buffers, maximum in-flight **bytes**, maximum allocation per operation, and a process-wide memory budget. Two admitted 2 GiB jobs can exceed 4 GiB before copies, outputs, WASM scratch, caches and UI state. A job count of two therefore cannot guarantee a process memory ceiling.

For proposed admission control, reserve before reading/dispatching: caller input retained by the pipeline, each private copy, worker input and output bounds, intermediate representation, decoder/WASM scratch, and retained result. Count shared backing storage once where views alias, count each private copy separately, and reserve runtime/UI/cache headroom. Release reservations on completion, cancellation, error, worker startup failure, and consumer release, not merely when work starts. A single request larger than the byte cap must stream or fail explicitly; it must not wait forever. With a slow sink, backpressure should stop file reads or job submission at the byte limit and resume after a verified release. A count-only queue cap does not meet this requirement when blocks vary in size.

Ownership has a parallel requirement. LZ4's default copy versus stable-until-flush option shows the tradeoff: avoiding a copy transfers a lifetime obligation to the caller. LFC-pack's Buffer candidate buys private ownership, but copying a concurrently written SharedArrayBuffer is not an atomic snapshot. Mutation after private-copy creation cannot change that copy; mutation during copying may yield mixed content. Mutation during synchronous WASM decompression was not tested. Any zero-copy proposal needs an explicit producer/consumer lifetime protocol and adversarial mutation tests before performance consideration.

## Controlled benchmark protocol and acceptance

For each proposed change, record exact base/candidate commit or uncommitted diff, runtime/compiler/browser, CPU and memory, input generator/seed, byte size, row count, cardinality, order, block/chunk size, worker count, warm/cold state and output hash. Use small/medium/large inputs and concurrency 1/2/4/8 where relevant. Run fresh processes for RSS and external/WASM peaks, repeat independent trials, report median and p50/p95/p99 with spread, CPU time, allocation count when available, bytes copied, largest intermediate buffer, maximum queued/in-flight bytes, time to first useful result, cancellation recovery and output equivalence. Keep throughput and latency conclusions separate from memory conclusions.

Pre-register product-specific limits. Pending those, a reasonable experiment screen is repeatable ≥10% median target-workload improvement with a confidence interval excluding zero, ≤5% p95 interactive regression, and ≤5% peak RSS increase unless a device budget explicitly allows more. A memory-budget experiment instead needs observed worst-case live bytes below its declared reservation ceiling under slow-consumer and oversize-input cases. Correctness, LFCP format, caller ownership, and cancellation violations reject an optimization regardless of speed. One warm microbenchmark or upstream percentage cannot satisfy these gates.

## Rejected approaches and next experiment

Reject adoption of LZ4, importing its worker count or benchmark percentage as a local tuning value, aliasing caller Buffers to save copies, a worker-count-only memory policy, unbounded whole-file staging where streaming is practical, speculative SIMD, and broad representation rewrites without measured bottlenecks. The next controlled experiment should be **LFC-pack queue byte accounting under a slow consumer**, using the isolated candidate and fresh processes. It has the strongest immediate evidence, a clear correctness contract and a testable memory limit. No optimization integration is authorized or proposed from the current measurements.
