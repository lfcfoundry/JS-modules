# Transferable performance engineering from LZ4 1.11 — 2026-11-10

This is the post-reconciliation expanded edition, preserved on this project handoff branch.

## Executive summary

LZ4 1.11 illustrates a useful split between independent worker jobs, bounded job queues, explicit source-buffer lifetimes, and a separate memory budget. Its API documents output lag and allocation behavior that make throughput, latency and peak memory separate measurements. The strongest near-term local experiments are LFC-pack transfer ownership and Workbench byte-aware import backpressure. No upstream benchmark predicts a local speedup, and no LZ4 dependency is proposed.

## Source and scope

Read the [Phoronix release article](https://www.phoronix.com/news/LZ4-1.11-Released), the [upstream v1.11.0 release notes](https://github.com/lz4/lz4/releases/tag/v1.11.0), and the [tagged frame API documentation](https://github.com/lz4/lz4/blob/v1.11.0/lib/lz4frame.h#L2211-L2387). The article reports multithreaded `liblz4` compression and a CLI `--memory` option; upstream specifies the actual API contract. These are source observations, not LFCFoundry benchmark results. No LZ4 dependency or repository usage search was part of this research.

Upstream demonstrates that `nbWorkers` can divide compression into jobs, with approximately `2 × nbWorkers` streaming jobs in flight. Jobs are usually 1 MiB, or one larger block, and the calling thread fills and emits them. Source input is normally copied; `LZ4F_srcStableUntilFlush` permits reading stable caller storage until flush. One-shot input fitting a job runs on the calling thread. Threads and buffers start on demand and persist in the context. The CLI has a separate `--memory` budget. The same release reports large workload scaling on its EPYC test machine, but also a sequential checksum and I/O ceiling and strong small-block gains from cheaper state reuse. These facts support experiments, not predicted LFCFoundry speedups.

## Bounded jobs are not a memory ceiling

A concurrency cap limits job count, not bytes. A bound on buffer count still permits a very large buffer. A bound on bytes in flight needs an accounting rule that includes queued input, private copies, worker input/output, intermediate representations, and retained results. A maximum per-operation allocation limits a single request but does not cap many concurrent requests. A process-wide budget needs admission control across all consumers plus a reserve for runtime and unrelated allocations. LZ4's documented job bound is therefore not a process-wide guarantee, and its CLI memory option is a separate policy.

For a proposed LFCFoundry worker pipeline, record an estimated reservation before accepting work: `input bytes + anticipated private-copy bytes + worst-case output bytes + intermediate bytes + per-worker state`. Release the reservation only when ownership and lifetime end. Test oversize single inputs, many medium inputs, cancellation, errors, delayed consumers, and a slow output sink. Backpressure should wait or reject with a clear policy when the byte budget is exhausted. Do not assume `worker count × average input size` is an upper bound.

## Benchmark protocol

1. Record repository commit, exact changed files, runtime/compiler, device CPU, RAM, OS, input generator/seed, data size, concurrency, and warm/cold state. Android results do not satisfy any required Linux x86_64 gate.
2. Preserve a baseline and candidate with identical inputs and output checks. Use fresh processes for RSS/heap peak and allocations; use enough independent trials to report median, spread and worst-case, not one best run.
3. Include small, medium and large inputs, and sorted, reverse, random, high-cardinality and mixed-length data where the component uses those shapes. Include zero-length and malformed inputs for correctness, separately from throughput.
4. Collect bytes/s, operation latency (p50/p95/p99), peak RSS, heap delta, external/WASM memory, allocation count where measurable, copied bytes, number and size of intermediate buffers, queue depth and bytes in flight, worker utilization and CPU, time to first output, correctness hashes, and error/cancellation behavior.
5. Set an adoption criterion before running experiments: a repeatable gain on important workloads, no material regression on other important workloads, unchanged public format/API/observable behavior, and a stated memory ceiling. Reject or redesign if any of these fail. Keep rejected candidate data in the handoff so it is not retried by assumption.

## Current priorities

Security and data integrity come first: bridge path approvals, LFC-pack transfer ownership, and Workbench empty-string correctness. Netflow correctness precedes speculative rendering optimization. The historical Workbench typed-index sort candidate was rejected across many scenarios; historical scatter array and SVG batching observations are not current adoption evidence. Do not import LZ4 or change LFCP format as a consequence of this research alone.

## Source-level evidence and version boundary

The [Phoronix article](https://www.phoronix.com/news/LZ4-1.11-Released) accurately identifies the library worker API and separate CLI memory option. The [tagged release notes](https://github.com/lz4/lz4/releases/tag/v1.11.0) and [tagged frame header](https://github.com/lz4/lz4/blob/v1.11.0/lib/lz4frame.h#L2211-L2387) give the operative details. The following are upstream observations, not local performance claims.

| Principle | Exact upstream evidence | Version-specific change versus general lesson |
|---|---|---|
| Independent parallel work | `LZ4F_preferences_t.nbWorkers` and frame header lines 2220–2237 partition jobs; independent blocks retain identical output, linked blocks can differ from single-thread output. | Library workers are new in 1.11; independent partitions and deterministic result ordering are general. |
| Bounded jobs | Header lines 2233–2245: usually 1 MiB jobs, a single larger block when needed, approximately twice the worker count in flight, output drained by flush/end. | Those sizes and bounds are LZ4-specific; counting jobs does not bound byte size. |
| Byte-aware backpressure | Header lines 2241–2251 defer completed jobs until output space exists; release notes describe CLI `--memory` separately. | CLI memory option is new in 1.11; global byte reservation is a proposed LFCFoundry policy, not an `nbWorkers` guarantee. |
| Process memory ceiling | Header lines 2262–2264 and 2315 describe retained worker states and job buffers; release notes describe `--memory=#` for the CLI. | LZ4 documents its own allocation behavior; a cross-pipeline process budget requires separate local design. |
| Data movement and ownership | Header lines 2253–2257 and 2383–2387: default copies input; `LZ4F_srcStableUntilFlush` reads caller memory after update until flush/end. | Stable-until-flush is the 1.11 multithreaded lifetime contract; explicit owner/lifetime is general. |
| Cache locality and small work | Release notes, “Faster on small data, and with dictionaries”: resetting reused state clears stale entries; measured gains vary by 1/4/16/64 KiB and compiler. | Specific cache-table change is 1.11; test data layout and state reuse locally. The release does not establish a universal cache-miss reduction. |
| SIMD and streaming | Header lines 2239–2251 and 2490–2532 define streaming and output bounds; release notes report an AArch64 decode-path gain. | Streaming API predates 1.11 and gets worker semantics in 1.11. The cited sources do **not** establish a new SIMD implementation; SIMD is only a local experiment hypothesis. |
| Incremental processing | Header `LZ4F_compressUpdate`, `LZ4F_flush`, `LZ4F_compressEnd` contract: output may lag input and `LZ4F_compressBound(0)` provides room for at least a job. | This worker-drain behavior is 1.11-specific; incremental pipelines and honest time-to-first-result are general. |
| Allocation pressure | Header lines 2303–2315 explain stack versus `LZ4F_HEAPMODE`, allocation/free tradeoff, and worker buffers; release notes explain reused contexts. | These are LZ4-specific allocation choices; measure GC/external/retained memory locally. |
| Intermediate representations | Header lines 2224–2245 separate input jobs and output emission, while lines 2253–2257 expose the copy option. | An inference: enumerate intermediate buffers in LFCFoundry before removing any. No upstream proof that a local representation is redundant. |
| Throughput and latency | Release notes show worker scaling and a sequential content-checksum/I/O ceiling; header lines 2239–2251 say streaming output can lag. | Upstream figures are workload/hardware-specific. The throughput/latency tradeoff must be measured against local interaction needs. |
| Workload scaling and predictability | Release notes compare small-block sizes, compilers, AArch64, and large EPYC work; header lines 2262–2267 start workers on demand and describe worker-creation failure. | 1.11 changes those paths; varied workload matrices and failure-path measurement are general. |

The frame header’s `nbWorkers` is marked experimental; dynamic lib builds support threading by default, while static builds may run serially and still accept the preference. The source header states a single-job input runs on the calling thread, output depends on content/parameters/flush points, and contexts retain worker resources. These are important when translating an API idea into a browser or Node worker pipeline. They do not imply identical implementation or speed in LFCFoundry. ## Explicit memory and concurrency model

Use separate limits for `maxConcurrentJobs`, `maxQueuedJobs`, `maxInflightBuffers`, `maxInflightBytes`, `maxAllocationPerOperation`, and `processBudgetBytes`. Admission reserves the estimated peak of input, immutable copy, worker scratch, bounded output, intermediate representations, and retained result **before** work starts. The process budget also reserves room for runtime, UI, caches, and unrelated components; those consumers must share a single accounting authority. Release reservations on completion, cancellation, error, and failed worker startup. If output is delayed, retain its reservation until the consumer releases it. If an individual request exceeds its per-operation cap, reject or stream it; waiting forever for a budget it can never fit is incorrect.

For example, two allowed jobs each accepting a 2 GiB input can require over 4 GiB before copies, output, and scratch. `maxConcurrentJobs = 2` therefore supplies no usable process memory ceiling. A buffer-count cap is also insufficient when buffer sizes vary. Backpressure must be byte-aware: pause file reads or worker dispatch when the reservation would exceed the budget, and resume after a verifiable release. Account for aliased views by backing store once, while accounting for private copies separately. SharedArrayBuffer may be concurrently mutated, so copying it without synchronization is not an atomic snapshot guarantee.

## Pre-registered local experiment gates

These are proposed gates to set **before** a controlled experiment, not claims that any candidate has met them. Run baseline and candidate with identical seeded data, verify exact outputs, and report the full distribution. For performance, require a repeatable median improvement of at least 10% on the named target workload with a 95% confidence interval excluding zero, no p95 latency regression above 5% on important interactive workloads, and no peak RSS increase above 5% unless a separately approved device budget permits it. These thresholds are starting policies and should be replaced by product-specific budgets where known. Correctness, format, owner/lifetime, cancellation, and memory-ceiling violations reject a candidate regardless of speed.

| Experiment | Measured acceptance evidence | Rejection evidence |
|---|---|---|
| Independent worker blocks | Large-input throughput meets gate at 2/4 workers; decoded bytes and ordering identical; small-input p95 within gate. | Sequential checksum/I/O dominates, worker overhead or output drift. |
| Chunk size and bounded jobs | Chunk sweep finds a stable throughput/latency range and fixed maximum chunk bytes. | Larger-than-chunk operations allocate unbounded memory, or batching delays first result. |
| Byte backpressure | Slow-sink stress stays below configured in-flight byte budget; queue wait and cancellation recovery measured. | Bounded job count but unbounded queued/retained bytes. |
| Process budget | Fresh-process peak RSS stays under declared device/process ceiling plus known measurement error across components. | Any accepted oversize request or retained allocation bypasses accounting. |
| Copy and ownership | All caller views remain usable; copied bytes and RSS/time recorded for offset, pooled, overlapping and shared cases. | Detachment, mutation race claimed solved without synchronization, or no material copy saving. |
| Cache/layout of data | Gains across the representative sorted/reverse/random/cardinality matrix with allocations and CPU separated. | One favorable distribution hides regressions or larger retained caches. |
| SIMD candidate | Architecture-specific speedup meets gate with scalar fallback and exact output on all supported CPUs. | Dispatch overhead, unsupported devices, or merely assuming upstream AArch64 gain implies SIMD. |
| Streaming / incrementality | Time to first useful output improves while total time and exact output meet gates; slow sink keeps bytes bounded. | A mandatory global stage nullifies incremental benefit. |
| Allocation and representation | Fewer measured allocations/intermediate bytes and lower or equal fresh-process RSS; exact observable behavior. | GC or retained-memory increase, changed row order/format, instrumentation loss. |
| Workload scaling | Break-even threshold stable across sizes, concurrency and fresh processes. | A single workload or warm-cache result is the entire case. |
| Throughput versus latency | Throughput gain meets gate without p95/p99 interactive regression or starvation. | Queueing raises tail latency despite higher jobs/s. |
| Memory-pressure predictability | Repeated constrained-memory trials remain under ceiling and recover after cancellation/errors. | OOM, stalled admission, or unpredictable RSS tail. |

## Ranked next experiments

1. **LFC-pack ownership/copy inventory** — high expected correctness value, low implementation risk. Use the isolated Buffer candidate and fake data to measure copy bytes, caller-view preservation, throughput and RSS. Do not treat a non-atomic SharedArrayBuffer copy as a solved concurrent-mutation problem.
2. **Workbench import byte inventory and backpressure prototype** — high expected memory value, medium risk. Trace queued and retained bytes at each stage with slow output; prototype budget accounting outside canonical code.
3. **Netflow grouping/serialization allocation profile after correctness review** — medium value, low risk. Run high-cardinality and control-character fixtures; preserve exact scene semantics.
4. **Story Editor worker end-to-end latency and copy accounting** — medium value, low risk. Existing equivalence harnesses establish computation parity, not message/lifecycle performance.
5. **Mind Mapper deep/wide layout and redraw trace** — lower expected value, low risk. Measure interaction thresholds before pursuing parallelism or incremental rendering.

Rejected for now: adopting LZ4, importing its thread counts or benchmark percentages as forecasts, reducing copies without an ownership contract, a worker-count-only memory policy, whole-input staging where streaming is feasible, speculative SIMD without a portable fallback, and broad representation rewrites before correctness baselines. No canonical project code or dependency is changed by this research.
